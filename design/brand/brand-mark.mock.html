Panel 1 — The logomark: four candidates for MOTIR-1140

No letterform. The mark is not an M and is not derived from one — an initial says only what the product is called, and Motir's name is not the interesting thing about it. Each candidate below is a mathematical object that is true of what Motir actually does. MOTIR-1140 (8.3.2) is a decision card, and a decision needs something to decide between: four candidates in two families — three flat, one with depth — all buildable SVG today, and picking any of them changes only the <path> data MOTIR-1150 consumes. The candidate with depth uses one colour at three opacities (100 / 58 / 36%), never a second hue, so the Tier-3 token rule holds and a data-palette swap re-skins it for free.

Flat — one closed form, one stroke weight, one colour

With depth — the same curve as B, given thickness and put on an angle. Orthographic, not isometric: the plate is tilted about the horizontal axis so the far edge lifts and the near rim comes into view, then rolled slightly in-plane. Two numbers describe the whole 3D form — a tilt and a roll — which is why it stays 7 paths instead of a mesh.

And it can move. The hypocycloid is not a drawn shape — it is generated, by a circle rolling inside a circle. That gives the mark two motions it owns by construction, rather than two effects applied to it. Both are shown live below; the frames beside each are what the still export captures.

Spin — the plate turns on its own axis

The curve's own spin parameter, not a CSS rotation of the finished image: the rim and the tone bands are recomputed per frame, so the solid genuinely turns rather than sliding around. Five-fold symmetry means a 72° rotation is a seamless loop — 12 frames, 2.4 s.

Morph — the curve changes its cusp count

Change the ratio of the two circles and the curve becomes a different member of the same family: n = 3 → 6 and back. This is the motion worth having, because it is the product's own argument — the plan is not a fixed shape, and the thing that changes it is one number.

Motion is decoration, never information. The mark animates only where it is already decorative and large: the OG card, the marketing hero, a loading state. It is static in the shell, in auth, in email, in the tab strip and at every size below 40 px. And all of it sits behind prefers-reduced-motion — the same gate globals.css already puts on the Plan-with-AI shimmer and the FAB pulse — with the static mark as the reduced-motion state.

Considered and dropped: the isometric cube (the Hasse diagram of B₃, which would have been candidate A one dimension up) and the Penrose tribar (locally consistent everywhere, globally impossible — a precise description of a plan that does not close). Both are mathematically apt and both were built and rendered. Both are also among the most heavily used marks in software — the cube is lucide's own Box — and a brand mark that reads as a stock icon is not worth the idea behind it. Also dropped: the astroidal ellipsoid (|x|2/3 + |y|2/3 + |z|2/3 = 1, the surface whose every coordinate cross-section is an astroid) — the most literal 3D answer to "the hypocycloid with depth", and too complicated: a faceted mesh of 80 paths that would need hand re-authoring to ship. Tilting the flat curve gets the same volume for 7 paths, and keeps the animation.

Recommendation to MOTIR-1140: A for the mark, D if the brand wants to move. A is still the only candidate legible at every shipped size with no second artwork, and it is the safer system. But D is the only one that can animate as itself — spin and morph both fall out of the construction rather than being effects laid on top — and if the brand is going to have a motion identity at all, that is worth more than the flat cut it costs. C and D both owe a simplified cut below ~24 px; A and B do not. B and D are the same curve, so picking one does not close the door on the other.

Panel 2 — Construction, clear space and minimum size

24-unit grid · the dashed box is the mark's true extent (20.1 square)

viewBox
0 0 24 24 — the same grid every lucide-react icon in the app uses, so the mark drops into any icon slot unscaled.
paths
M12 3.2L20.8 12L12 20.8L3.2 12Z and M12 7.6L16.4 12L12 16.4L7.6 12Z — two closed rhombi, the inner at exactly half the outer's half-diagonal (8.8 → 4.4). One number generates the whole family: the next level in would be 2.2.
paint
fill="none", stroke="currentColor", stroke-width="2.5", stroke-linejoin="round". No stroke-linecap — both paths are closed.
extent
x and y both 1.95 → 22.05 (20.1 square), centred on (12, 12) by construction — a consumer centres it by geometry, with no nudge. The mark occupies 84% of the box, which is why it holds its own beside a 24 px lucide icon rather than reading smaller.
clear space
2 × the stroke weight = 5.0 units (21% of the box edge) on all four sides, measured from the extent above — never from the viewBox. A rhombus reads with more air around it than a square of the same extent, so this is the floor, not the target.
minimum size
16 px for the bare glyph — the stroke lands at 1.67 px and the inner rhombus at 2.9 px across, still an unmistakable rhombus. Below 16 px use the tiled form (Panel 5), which keeps the glyph at 66% inside a solid field.
colour
ONE colour. The mark is monochrome by construction — it never carries a gradient, a second hue or a shadow.

Panel 3 — Wordmark and lockups

face
Inter, weight 700, tracking -0.02em — already loaded by app/layout.tsx, so the wordmark costs no new font payload.
the pin
The wordmark MUST read font-family: var(--font-sans-source), … — the raw FACE variable — and never var(--font-sans), the role token. [data-type='motir-mono' | 'grotesk' | 'mono-technical'] each re-point --font-sans, so a wordmark riding the role token changes typeface when a user picks a type pairing in Appearance. This is not hypothetical: it is what the shipped ExploreTopBar does today (Panel 0a). The mark is brand; the type axis is chrome; they must not be wired to the same variable.
proportion
wordmark font-size = 0.72 × glyph box; gap = 0.33 × glyph box; baselines optically aligned by centring the wordmark's cap-height on the glyph's extent, not on its viewBox. At the 32 px glyph that is 23 px type on a 10.5 px gap.
colour
glyph --el-accent-on-surface, wordmark --el-text. Two tokens, both themes, no exceptions.
where fonts cannot be relied on
next/og renders outside the CSS tree, so the OG template must pass the Inter face through ImageResponse's fonts option (Panel 6). It ships fontFamily: 'sans-serif' today, which is why the current card's "Motir" is set in whatever face the renderer happens to have.

  • The dark variant is a token choice, not a second asset. The glyph paints currentColor and the lockup sets color: var(--el-accent-on-surface), which resolves to #5645d4 light and #7b6ce5 dark on its own. There is no brand-dark.svg to keep in sync.
  • Use --el-accent-on-surface, not --el-accent. The two are the same colour in light and diverge in dark — --el-accent is the darker FILL, built to carry white ink, and it loses 0.8 of a ratio point as a glyph. This is the row marked above.
  • Never --el-text-inverted. It is var(--color-background): white in light, #0f0f0f in dark. It is the ink FOR a filled field, so a mark painted with it disappears on the page background in light mode — the exact flip the card warns about. On a filled tile, the correct ink is --el-accent-text.

Panel 5 — Favicon and app-icon set

app/favicon.ico (16 + 32, the only icon that ships today) stays as the legacy fallback. Everything else below is new. Sizes are drawn at their true pixel size.

corner radius
icon.svg rx = 32 × 0.22 = 7; apple-icon rx = 180 × 0.22 = 40. 0.22 is --radius-lg (12) over a 56 px tile — the app's own container ratio, so the icon reads as the same family as the UI. The maskable pair has rx = 0.
safe zone
Maskable: the glyph sits inside the centred circle of diameter 0.8 × canvas. A rhombus makes this cheap — its extreme points lie on the axes, not at bounding-box corners, so its circumradius is only 10.05/24 = 0.419 × the glyph box, or 0.55 × canvas across at the 66% render used here. Comfortably inside 0.8. (A square or a letterform pays √2 for the same extent and has to be shrunk to fit.) Non-maskable: the same 66%, centred.
manifest
app/manifest.ts declares both maskable entries with purpose: 'maskable' plus name: 'Motir', short_name: 'Motir', theme_color = the light --el-accent literal, background_color = the light --el-page-bg literal. A manifest is static JSON and cannot read a CSS variable, so these two are hex literals whose provenance is recorded here.
the ico is not enough
Next.js only auto-wires files it finds: app/icon.svg, app/apple-icon.png and app/manifest.ts each have to EXIST. None do today — which is why an iOS "Add to Home Screen" currently gets a screenshot of the page.

Panel 8 — Accessible names: decorative vs informative

The same glyph is decorative in one slot and the entire accessible name in the next. The rule is about the CONTAINER, not the mark: if the visible wordmark is beside it, the glyph is decorative; if the glyph stands alone, it carries the name.

Slot Form Markup Accessible name
Shell top bar (7a) mark only, is a link <Link aria-label="Motir — go to dashboard"><svg aria-hidden> informative — the link's label
Auth card (7b) lockup, is a link <svg aria-hidden> + visible "Motir" decorative — the text names the link
ExploreTopBar (7c) lockup, is a link <svg aria-hidden> + visible "Motir" decorative
PublicTopBar (7d) quiet lockup, is a link <svg aria-hidden> + visible "on Motir" decorative
Email (7e) image, not a link <img alt="Motir"> informative — images are often blocked
Favicon / app icon (5) image, OS chrome manifest.name = 'Motir' informative — the manifest name is the label
OG card (6) image, social embed export const alt informative — the only name an embed gets
  • Never both. An aria-label on the link plus a visible wordmark inside it makes a screen reader announce "Motir" twice, or announce the label and silently drop the visible text. Pick one per slot — the table above IS the pick.
  • The wordmark stays live text. It is never baked into the SVG on a DOM surface, so it is selectable, translatable and searchable — and it survives a user's font-size preference. (next/og and email are the two exceptions, and both are raster surfaces.)
