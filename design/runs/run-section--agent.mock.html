RUN IN MY AGENT — on the work item

MOTIR-6864 · MOTIR-7022. A DELTA on MOTIR-684’s run-section--hosted.mock.html and run-modal--hosted.mock.html: only what changes when a developer sends a ready work item to one of their own agents — the control and picker beside Run hosted, every refusal in words, the start, and the run in the section and the modal, labelled with the agent and its coding agent, costing machine time only.

It composes the shipped surfaces. The section chrome, the pills, the six phases, the end lines, the cost figure, the cancel confirm and the modal are the hosted delta’s own classes. What is new is the control and its popover, the In my agent lane chip, the agent line, and the copy.

0THE ACCESS PATH — Run in my agent joins the Run section’s header, to the LEFT of the hosted door.

The header slot is the one RunHostedButton already renders into: ContentSectionCard’s headerRight on the Run section, the head of the item page’s late stack, directly before Development (app/(authed)/items/[key]/_components/LateSections.tsx). Nothing else on the page moves.

Order: Run in my agent, then the model picker and Run hosted. Run hosted keeps the right end it shipped with, so nobody who already uses it has to find it again, and it stays the one PRIMARY button in the header. Run in my agent is a secondary button with a trailing chevron, because it opens a choice (which agent) rather than doing the thing. Where the hosted lane is off (hostedDoor null) the header carries Run in my agent alone, at the right end.

Who sees it: anyone who can edit the work item on a deployment where My agents exists (the rail entry’s own condition). It is the developer’s OWN agents that it offers, so a person with none still sees it, and it sends them to My agents (panel 3).

1THE PICKER — the developer’s own agents on this project; choosing one STARTS the run.

The control opens the shipped Popover under it, right-aligned with the header. It lists what GET /api/work-items/[id]/agent-runs/agents answers (decision §4): the caller’s own agents on the work item’s project, each with its name, its state (the list’s RunTonePill through AGENT_STATE_TONE, so the picker and My agents never disagree), its coding agent and its recorded sign-in. There is no Start button: pressing a row that can take the run is the start, and the popover closes on the press (panel 5).

Agents on OTHER projects are not listed. An agent is made for one project and holds that project’s repositories in its home; a row for another project’s agent could never be chosen, so it would only be noise with a reason attached. The footer says so in one line. The agent_instance_wrong_project refusal still has words (panel 4) for the race where a stale list is pressed.

Sign-in is the RECORDED probe (decision §4: taken at every boot and before every hibernate), which is why a hibernated agent can say it. Signed in and can’t be checked may start; not signed in may not (panel 2). Rows are ordered as My agents orders them. Keyboard: the listbox’s arrows skip a row that cannot take the run, Enter starts, Esc closes and returns focus to the control.

2EVERY AGENT STATE, AND EVERY REASON A ROW CANNOT TAKE THE RUN — one row each, in the picker.

The seven AgentInstanceState values. running, hibernated, starting, waking and failed can be chosen: the launch job wakes a hibernated or failed agent, and waits for a starting or waking one (decision §4: “A starting or waking agent is not refused”). Each says what will happen first in its sub-line. hibernating and deleting cannot (agent_instance_state_conflict) and say why.

Below the states, the row-level refusals the agents read already knows before anything is pressed — a run already live in the agent (named and linked), an image from before the launcher, a coding agent with no unattended command, not signed in — each drawn as a row that stays in the list, cannot be chosen, and says in words what would fix it. A disabled row is never hidden: an agent that disappears from the list reads as an agent that is gone.

Ink on these rows is --el-text / --el-text-secondary on the popover’s --el-page-bg, and on the focused row’s --el-option-active-bg; a disabled row’s NAME drops to secondary, its reason stays full ink because it is the sentence to read.

4EVERY START REFUSAL, IN WORDS — on the door, never in the timeline. Nothing starts.

Decision §4’s refusal set. Every check runs BEFORE the run is opened, so a refusal leaves no run behind — no history row, nothing in /runs, nothing for the modal — and lives on the door exactly as the hosted refusals do (HostedDoorNotices): the warning notice (--el-warning-surface, --el-warning glyph, --el-text-strong ink) under the header, a title that begins Not started —, and a body that ends Nothing was started and nothing was charged. That shared first and last phrase is what makes eleven different reasons read as one family.

The row-level reasons in panel 2 are the SAME refusals seen before the press; these faces are what a press answers when the list was stale (another tab signed out, a run started elsewhere). The picker re-reads its list on any refusal, as the hosted door re-reads its models. hosted_repository_not_writable is the hosted door’s shipped notice, unchanged (its words are the run’s, not the lane’s), and is not redrawn.

6STARTING — one press wakes the agent if it must, then starts the run. What the section shows between the press and the first event.

The press answers with the run id at once (decision §4: the route opens the run, claims the work item and hands the rest to a durable launch job). So the section flips on the response, not on the machine: the popover closes, the header becomes Cancel run, the pill reads Running, and the timeline is the six hosted phases with Starting current. No new phase and no new event kind — waking is part of Starting, and its detail line says so: Waking yue-codex when the chosen row was hibernated or failed, Starting in yue-claude when it was running. The builder takes that from the row that was pressed; nothing is re-read to draw it.

Between press and response the chosen row shows the Button’s own loading state and the control reads Starting… (the hosted door’s string). A wake is a cold boot of about a minute; the Starting row stays current through it, and the run’s first CLI event (checkout_ready) moves it to Cloned. If the live sign-in probe after the wake finds the coding agent signed out, the run closes Failed with that reason (panel 8).

7RUNNING and SUCCEEDED — the run names its agent and coding agent; the cost is machine time only.

The agent is said three times on purpose, in three registers: the In my agent lane chip (the hosted chip’s shape, the terminal glyph), the line Working in yue-claude · Claude Code with Watch it in My agents (/my-agents?agent=<id>, where the run’s session can be watched — the panel mock), and the meta row: Lane In my agent · Agent yue-claude (the same link) · Coding agent Claude Code · Elapsed/Took. There is no Model: the model is whatever the developer’s own agent is set to, and Motir does not read it (decision §5, model = null). The Running phase’s detail is Claude Code · yue-claude where a hosted run says opencode · {model}.

The cost is ONE figure: Machine time — the run’s own duration, labelled as the agent’s running time charged with the agent. No Tokens figure and no Credits figure: no gateway key is minted and no usage row is written (decision §5), and the credits the machine time costs land on the agent’s interval, shown on My agents’ list, where they can be compared across agents. Showing a credit number here would be a second, per-run price the record does not have. On success the pull request is the headline and the end line is the hosted run’s own (The run delivered its work.); the work item moved to Implemented, as for every run that opens its pull requests.

8FAILED, CANCELLED and TIMED OUT — each with the reason the run recorded; the work item stays where it was.

Every DispatchRunStatus end, in the hosted grammar: the pill from the tone table, the end line (runs.hosted.end.*, shipped), the RECORDED reason quoted verbatim in mono under it, then This work item stays where it was — work the agent pushed is on the run’s branch. (run-death-keeps-work.md §3, for every origin). The reasons are the record’s (decision §6), rendered, not catalogue copy: agent exited with code 1 · the agent stopped · the agent’s machine was lost · out of credits · the coding agent is not signed in · stalled: no agent output for 15 minutes · the 12-hour backstop’s line.

“The agent stopped under the run” is Failed, not Cancelled: nobody chose it. Timed out keeps the warning mark on the phase it ran out in (.tlRow.is-late) — unknown is not failed. After every end the doors are back: Run in my agent (it never says “again” — the next run may be in another agent) and Run hosted again when the last run was hosted, otherwise Run hosted.
