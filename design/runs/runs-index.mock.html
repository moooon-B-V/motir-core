The RUNS INDEX — /runs

MOTIR-1789 · MOTIR-3893. Every run this project has made, current and past. It is the surface that makes a run FINDABLE — and until it exists, every door into a run starts from something the reader already holds: an id, or a work item they already know is in the set.

It replaced a door that could not exist. The obvious place for this was an indicator on the dispatch queue, and that is the one place it cannot go — dispatching a work item is precisely what removes it from that list (MOTIR-3914). What looked like a smaller feature was a missing surface.

It composes, it does not invent. The table is the shipped TableShell grammar from the jobs dashboard; the tones are design/runs/design-notes.md’s table, reused; the rail rows are the shipped sidebar’s shape. Nothing here is a new colour, a new radius or a new status vocabulary.

0THE ACCESS PATH — a primary rail entry, directly after Ready.

Read against design/shell/design-notes.md and the shipped convention in app/(authed)/_components/SidebarNav.tsx: every top-level project view is a primary entry — Home · Dashboard · Issues · Ready · Boards · Roadmap · Plans · Backlog · Triage · Reports — and each carries a comment naming the design section that grounded it. A runs index is a peer of those, so it earns the same first-class row. Ready is where you dispatch; Runs is where you watch, which is why it sits directly after it rather than at the end.

The glyph is Waypoints — a path through ordered nodes, which is what a run over a SET is, and it is unused. Not CirclePlay (Ready holds it), not Zap (the epic issue type), not Activity (Code health) and not History (Resume onboarding).

The row is registered as well as rendered. lib/settings/projectNavAccess.ts carries one row per nav href with a permission requirement and an evidence sentence, and its own header records that canOfferNavDestination answers FALSE for an href it does not carry — so an omission does not fail loudly, it drops the row from the rail. A page that ships, renders and passes its tests can still be invisible.

Requirement: browse-only, because the read’s own gate is projectAccessService.assertCanBrowse — a run history is project data, and whoever may see the project may see what ran in it. That is the same answer the two sibling run reads already carry in the permission inventory.

1THE INDEX — current above, past below.

Two sections, not a switch, and not one undivided list. A person arrives here asking one of exactly two questions — what is happening right now or what happened — and the answers are read differently: the first is watched, the second is searched. Two headed sections answer both without a click and without hiding either, which a switch cannot do and an undivided list makes you scan for. Live runs are few by construction (they are bounded by how many agents are running), so the top section is short and the page does not fight itself.

The whole row is the link. Each carries the COMMAND that opened the run, the scope it named, the agent and model, when it started, elapsed-or-duration, its status, and the leg summary — “9 of 11 implemented, 1 skipped, 1 not reached” — which is the run’s outcome in one cell and is read off counts the page already has.

4THE TWO ROWS A LIST OF RECORDS HAS TO SURVIVE.

A run with NO work items — it claimed nothing, which is a real outcome and not a failure: a scoped run whose members were all skipped, or a batch whose snapshot came back empty. It reads took no work items, in the neutral tone.

A run whose SCOPE work item was DELETED — the row survives it. The run record stores the scope LABEL beside the id precisely so a run stays readable after its subject is gone; the cell says so rather than rendering an empty column or a dead link.

Command Scope Started Status Work items
motir run sprint Sprint 13 4 days ago Succeeded Took no work items
motir run MOTIR-3412 (deleted) 5 days ago Succeeded 3 of 3 implemented

Neither row is styled as a problem. A deleted scope is a fact about the tree, not about the run — and a run that took nothing did exactly what it was asked to do.

5THE WAIT, and THE FAILURE.

This page owns its own wait — unlike the run section, which fills with the item page’s ONE settle. The frame keeps the table’s geometry so nothing shifts when the rows arrive, and it is an in-page boundary, never a loading.tsx: a route-level boundary here would sit above /runs?run=<id>, flush the response head and turn that page’s 404 into a 200.

A failed read says what failed and offers the retry. It does not empty the page, because we could not load this and nothing has run are opposite facts and must never share a face.

6AT SCALE — paged, because this list never stops growing.

Run headers are append-only and nothing deletes them. The retention sweep clears event BODIES after 30 days; it removes no rows. A project running motir auto nightly accumulates a run per night for as long as it lives, so a load-everything read is not a shortcut here — it is a page that gets slower every day and never gets faster.

Paging, not virtualization, and the reason is the partition above: the live section is short by construction and the past section is what grows, so there is one growing list and it has a natural stopping point — a reader looking for a run from last week does not scroll, they page. Drawn against 25 rows a page, the read’s own default, with a cursor rather than an offset so a run opened mid-read cannot shift a row across the boundary. The ORDER is startedAt DESC, id DESC — total, because the id breaks the tie.

No count is promised beyond what the page holds: the total is what the read reports, and a project with three thousand runs is told the truth rather than shown a spinner.
