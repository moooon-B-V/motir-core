A container’s OWN runs — the door, and /runs?scope=

MOTIR-5402 · gates MOTIR-5363. When a story is handed to an agent as one piece of work, the run is recorded against the story’s children: a scoped run’s legs are its members, and the story has no leg of its own. So the one page a person opens to ask what happened to this story? answers No runs yet.

The answer already ships; only the surface is missing. dispatchRunService.listRunsForProject takes a scopeWorkItemKey, resolves it inside the project and reads dispatchRunRepository.listByScope — indexed on [scopeWorkItemId, startedAt] and routed as GET /api/projects/[key]/dispatch-runs?scope=. Nothing in the product sends it.

It composes, it does not invent. The section is run-section.mock.html’s card, list and empty state. The page is runs-index.mock.html’s header, its two sections, its table and its wait / failure faces. No new tone, colour, radius or primitive.

1RUN AS A SCOPE, NEVER AS A LEG — the door, where the false empty state was.

The Run section on a container that has been a run’s scope. It no longer says No runs yet: in its place is a scope block — a sub-heading, the latest run over this work item’s children as ONE row in the section’s own recent-runs grammar, and the door to all of them. The section header’s pill is that run’s status, from the area’s tone table. There is no step timeline: steps belong to a LEG, and this work item has none.

The read is the shipped one, at one row: listRunsForProject(projectKey, { take: 1, scopeWorkItemKey }) — made beside the section’s leg read in lateReads, and only for a work item that has children, because the CLI records a scope only when it claims a container (commands/dispatch.ts, the run_scope path). The row carries the command, agent, status, start and the leg counts, so the line and the pill need nothing more. No count is shown — no count read exists, and a number here would be a new read; the narrowed index is where the rest is.

5THE ADDRESS CONTRACT — scope survives opening and closing a run.

The parameter is scope, and it takes a work-item KEY. It composes with the modal’s run: a run opened from the narrowed list is ?scope=…&run=…, and closing it returns to the narrowed list. Today the index writes /runs?run=<id> and /runs literally, which would drop the narrowing on the first click — so the build keeps every other parameter when it adds or removes run.

Which navigation, by CLAUDE.md’s discriminator — does the target body need data the browser does not have? Entering or leaving a scope changes both server reads the page makes, so it is a real navigation. Opening or closing a run does not: the modal fetches its run client-side.

From Action Address How
Item page · Run section the door, or the scope row /runs?scope=MOTIR-1789 a link — a route change; the server reads both sections narrowed
Narrowed index open a run /runs?scope=MOTIR-1789&run=run_7f2c shallowPush — keeps a history entry
Run modal close · ESC · Back /runs?scope=MOTIR-1789 shallowPush (Back pops the entry)
Narrowed index All runs /runs a link — a different server read
Narrowed index the scope’s key in the subtitle /items/MOTIR-1789 a link — back to the work item

A key typed in lower case resolves — the service upper-cases it — and every link the product writes uses the upper-case key. A run that is not a run of that scope still opens: the modal reads the run by id and does not check it against the list behind it.

7THE KEY RESOLVES TO NOTHING — a different fact from empty, so a different face.

The route answers 404 for a key that is not a work item in this project, and it does so on purpose: has no runs and is not yours are opposite facts. The page must not collapse them either. Three faces, three glyphs: empty is the bot and a command (panel 6); unresolvable is search-x on the info ground, no command and no retry (here); a failed read is the alert with Try again (panel 9). The copy cannot say which of deleted and not visible to you it is, because the route deliberately does not tell it.

A deleted scope lands here too, and its runs are not lost. Deleting a work item sets its runs’ scopeWorkItemId to null (onDelete: SetNull), so they are no longer addressable by scope — and they stay on /runs under their stored label, drawn as MOTIR-3412 (deleted) in runs-index panel 4. The copy points there.

10WHAT ?scope= CAN NEVER ADDRESS — and where those runs are instead.

?scope= reads scopeWorkItemId, and that column is set in exactly one place: the scope path of motir run, when it claims a CONTAINER (dispatchRunService.ts connects the scope from the key the CLI sends). Every other run has none, so none of them can be narrowed to, and none of them is missing — each is somewhere a reader can already go.
