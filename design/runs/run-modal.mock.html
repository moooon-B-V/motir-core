The RUN MODAL — full screen over /runs

MOTIR-1789 · MOTIR-3893. Click a run on the list and it opens over the list: the run’s own header, the reused canvas on the left carrying every work item the run owns and what state each is in, and the log pane on the right carrying what the agent is actually saying. Close, and you are back on the list where you were.

It is an overlay, not a route. A run is something you look INTO from the list and come back out of; a page loses the reader’s place and turns a glance into a round trip. There is no /runs/[id] — the deep link is /runs?run=<id>, written with shallowPush, so Back closes it.

The canvas is COMPOSED, not redrawn. The spatial canvas — its pan, zoom, drill, search, locate, saved layout and the work-item node’s look — is design/roadmap/’s, shipped as ProjectRoadmapCanvas. What this asset draws is the one thing a RUN adds to a node: that member’s disposition in this run.

0THE OVERLAY — and the way OUT, drawn rather than assumed.

The list stays mounted BEHIND it. That is the whole reason this is an overlay: closing returns the reader to the same scroll position and the same current/past partition, so the run they just read is still under the cursor.

Three exits, all of them real: the close control, ESC, and Back — because the deep link is a shallowPush that keeps a history entry. ⚠️ The canvas has its own key handling (/ to search, zoom, locate); a full-screen canvas inside a dialog is exactly where two ESC handlers collide, so the dialog’s must win and a test must say so.

2THE RUNNING EDGE — the run travels along it, and that is the point of drawing a graph at all.

A table of the set can say this one is running. Only the graph can say what becomes reachable when it lands, and that is the question a person watching a run actually has. So every edge FROM the running work item TO one it BLOCKS flows, in the running tone this area already owns — the arrow already points blocker → blocked, so the motion travels the way the work does.

Only running flows. A queued node's edges are dependencies, not travel; a finished run has nothing in motion and every edge is still. So a run that has stopped reads as a still graph, which is the correct picture of it.

⚠️ Reduced motion is REQUIRED, not a courtesy. This surface is left open for an hour at a time. Under prefers-reduced-motion: reduce the edge keeps its WEIGHT and its HUE — it still reads as the live one — and simply stops travelling. Drawn below, second.

⚠️ And a PNG cannot show motion, so what the export carries is the dash pattern and the arrow. Open the mock in a browser to see it run.

This needs a capability PlanningCanvas does not have today — MOTIR-3972 adds it.

CanvasEdge.variant is a closed union — firm · pending · cross — and the consumer supplies edges while the FOUNDATION renders them, so a consumer cannot animate an edge it does not draw. The variant is one member wider, and the animation must ride the SAME <path>: that file keeps its arrowhead markers in a separate <svg> precisely so the edge path count stays equal to the edge count, and a second element per edge would break the guard that asserts it. Five files compose this foundation, so the variant is opt-in and every other consumer must render byte-identically. MOTIR-3972 makes the variant available; this surface chooses which edges carry it.

3A FROZEN BATCH SNAPSHOT — an arbitrary set, and every skip with its reason.

motir batch and motir auto take whatever was ready, ACROSS parents — so the level the canvas serves is the run’s own SET, not one parent’s children. That is why the pane feeds loadLevel a synthetic level rather than a drill.

All SEVEN skip reasons, not six. batchPlan.ts’s SKIP_LABEL carries six; the schema’s DispatchSkipReason adds blocked_in_scope, which only a claimed scope produces — drawn where it can occur.

What the record does NOT hold is not drawn. A batch’s newlyReady group has no column; not_reached is a disposition and blocked_in_scope a skip reason, and those are the shapes available.

5THE LOG PANE’S THREE SILENCES — and collapsing them is the defect.

Sending log bodies is OPT-IN and off by default, enforced on the operator’s own machine: motir help — “the machine that holds the content is the machine that decides whether it leaves.” So the ORDINARY run has nothing here, and the pane must say why in a way that reads as the operator’s choice rather than as a failure to record.

One message for all three tells a person their run failed to record when in fact they chose that, or when the record simply aged out of its 30-day window.

8THE DEEP LINK — /runs?run=<id>, and three files agree on it.

It opens the list with that run’s modal already open and its row scrolled into view. The run SECTION on a work item points its “one of N” line and every run-history row at it, the runs INDEX writes it when a row is activated, and the modal reads it. Three files, one parameter name — so it is recorded here rather than in whichever is written first.

It is a shallowPush, not a router.push: the modal’s body is fetched client-side, so the server has nothing to answer. Keeping the history entry is what makes Back close the modal.

/runs?run=run_a91f — the index, that run open.

There is no /runs/<id>. A link to one would fail as a missing route rather than as a defect.

9WHAT THE RUN PRODUCED — where it lives, and the ABSENT case drawn first.

Most runs produce neither, so the absent case is the DEFAULT case and it is drawn first on purpose. A region that is present and empty on every ordinary run trains a reader to skip exactly the place the rare, important thing appears. So there is no region: the log pane simply starts at the log, with no heading, no rule and no “no findings” box.

It is PINNED ABOVE THE LOG, in the right pane — not a band under the header. A band spanning both panes would push the canvas down on every run to serve the few that have anything to say. The right pane is already the run’s NARRATIVE column — what the run said and printed — and a strip there collapses to nothing without moving anything else.

And a marker rides the NODE. The decision made both events CARD-scoped (run-findings-protocol.md Q5), so the record knows which leg produced each one. The strip answers what did this run produce; the node answers which work item produced it. Same fact at two zooms, and neither invents an attribution the record does not hold.

10THE PLAN, in its two states — an ASK and a piece of NEWS, and they must not look alike.

Submitted and waiting is the common case — auto-approval is opt-in and auto-only — and it is an ASK: nothing moves until a person decides. Approved by this run is NEWS: it already happened, and the thing it changed is the reader’s own tree. Somebody scanning a finished run at 09:00 must be able to tell those apart without reading a word of them, so the ask carries the accent rule and the only action affordance on the strip, and the news does not.

⚠️ NAMED PLAN BY PLAN, never a count. Not a preference — the terminal already settled it, in the comment above the block that prints this: “A count would tell an operator that their tree moved without telling them where.” The surface prints the same shape the terminal does: the plan, the work item it was approved FOR, and how many proposals it materialized.

A re-plan is a CORRECT OUTCOME, not a failure — renderReplanSubmitted’s own first line says so, and a surface that rendered it in a failure tone would teach people to distrust the most useful thing the loop does. It reuses this area’s replanned tone, which is deliberately neither green nor red. No new tone is defined here.

11THE BUG — one, several from one run, and one that has since been closed.

A filed bug is purely additive: it blocks nothing, claims no scope and did not end the run (run-findings-protocol.md Q3). The row says so by what it does NOT carry — no status transition, no blocking language, no call to act. It is a link and a title.

Several from one run stay separate rows. Collapsing them to “3 bugs” loses the only thing a reader wants — which three — and repeats the count mistake the approved-plans block already refuses.

A closed or archived bug still renders. The run found a real defect; somebody later triaged it. That is history the record exists to keep, so the row stays and the state rides it as a pill. It is never dropped, because a dropped row says the run found nothing.

12EVERY STATE THE RECORD CAN BE IN — including the three that get improvised.

A DECLINED plan is the most informative row on the page, not an error. The run said I submitted this and that stayed true; a person then said no. The row keeps the run’s own event wording and carries the plan’s CURRENT status beside it — it is never re-worded into a failure, and it is never hidden.

A target that is gone renders from the RECORD ALONE. Deleted, or not visible to this reader: the pointer resolves to nothing and the row is drawn from the event’s own data — the key and title it recorded — with no link. ⚠️ It must not be dropped and must not become an empty state; both would tell the reader the run found nothing when it did. Same posture dispatch_run_card.workItemKey already takes for a deleted work item.

Reporting-offline says the record is INCOMPLETE, not that the run produced nothing. This is the honest-gap case, and it is the one place the strip appears with no findings in it: silence and “the machine stopped reporting” are different answers, and only one of them means there was nothing to say.
