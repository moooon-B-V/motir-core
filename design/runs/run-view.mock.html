The RUN VIEW — /runs/[id]

MOTIR-1789 · MOTIR-3893. One dispatch run: what it CLAIMED, what it is working, what it left out and why, and where it stopped. The set is the part no board can show and no unit test can prove — and the part a person most needs while a run is in flight.

The set arrives in three shapes and the page is TOTAL over all three. A claimed scope, a frozen batch snapshot, and a single card — which is the degenerate case of the same object, drawn as the same table with one row rather than as a different page. A view that only draws the plural shape gets improvised for the singular one.

Every word of the vocabulary is the shipped one. The stop reasons, the skip reasons and their sentences are read from packages/cli/src/autoLoop.ts, packages/cli/src/batchPlan.ts and packages/cli/src/scopedRun.ts. Nothing here says something the terminal does not already say.

4THE ROW — every disposition, and the DELIVERY by reference.

The disposition vocabulary is the shipped enum, entire: queued · running · integrated · implemented · failed · replanned · skipped · not_reached. A renderer that is not TOTAL over it is the silent-default failure this codebase has already paid for once — a row that reads queued because nobody wrote a case for replanned is indistinguishable from a row that is queued.

The delivery cell is a REFERENCE and not a second drawing. Repository, PR number, CI state — three facts, read from the shipped delivery set. The full treatment is design/work-items/delivery-set.mock.html’s, and a second CI verdict on one product is how two screens start disagreeing about whether a card is green.

Queuedowned by the run, not started
Runningan agent is on it now
Integratedon a session branch
Implementedits own pull request is open
Failedthe agent exited non-zero
Re-plannedrefused the card; a plan is waiting
Skippedalways shown WITH its reason
Not reachedthe run stopped before it

Not reached shares queued’s tone deliberately. Both mean nothing ran; the label is what tells them apart, and inventing a ninth tint to carry a distinction the reader does not need is what the area’s tone table refuses.

7FINISHED — once per stop reason, because they are not one state.

halted and drained are opposite news and must not share a face. Each line below is the sentence the CLI already prints, and the pill is the run’s own status — which is DERIVED from the stop reason, so re-planned is a SUCCESS: the agent did the right thing.

Cancelled interrupted (Ctrl-C)
Succeeded stopped between cards — the card just finished is not ready to build on
Timed out the machine stopped reporting; the server’s reap closed the run

Timed out is written by the server, never by a client — a process that died cannot report anything, and Running is the most reassuring possible way to render a dead run. Warning tone rather than danger: unknown is not failed.

8REPORTING-OFFLINE · RECONNECTING · A DELETED CARD.

Reporting-offline is the state only a BYOK run can be in, and the one most likely to be improvised if nobody draws it: the run happened, the machine could not say so. Reporting is best-effort by design — a 500, an expired token or a dead network must never break a run — so what reaches Motir is a run that opened and then went quiet. It must not read as failed: the work may have shipped perfectly, and the Development section on each card is where that is answered.

Reconnecting is a TRANSPORT state, not a run state. The notice sits above the table and the run’s own pill keeps saying Running, because the run did not change — our connection to it did.

9THE DOORS IN — three, and none of them is /ready.

The runs index is the general one, and the only one that works without already holding something: /runs, from the rail. The container’s own surface — the story or sprint the run’s scope names — reaches the runs it is the scope OF. The work item’s run section carries the “one of 11 cards in this run” line, which is the fact a person opening a card mid-run most needs.

A fourth door was drawn once and is archived: an indicator on a /ready row. That row cannot occur — the ready set lists only not-yet-started work, and claiming a card is what starts it. See design/runs/design-notes.md § What this area drew once.

/runs the rail entry — every run, current and past
/items/MOTIR-1789 the container the scope names — the runs it is the scope of
/items/MOTIR-1792 a member card’s run section — “one of 11 cards in this run”

At scale. A sprint run claims every member of an active sprint — tens of cards in ONE view, not three. The table is drawn against 40 rows and keeps a stable order (the run’s own stored position); past that it PAGES rather than virtualizing, because the set is bounded by the sprint and a reader wants the whole ordered list rather than a scrolling window. No load-everything read: the set is fetched with the run, and the events stream separately.
