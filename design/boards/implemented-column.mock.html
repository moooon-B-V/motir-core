Implemented — the eighth board column, and the status chip

Design asset for MOTIR-3002 (story MOTIR-2999). It extends design/boards/board.mock.html and design/boards/board-scale.mock.html; it does not redraw the board. Every column, card, chip, table row and picker below is the real shipped markup, dumped from the components themselves — see “How this asset was produced” in design/boards/design-notes.md.

Panel 0 — the board at EIGHT columns (not seven)

The default workflow already ships seven statuses, not six: todo · blocked · in_progress · planning · in_review · done · cancelled (lib/workflows/defaultWorkflow.ts — planning arrived with MOTIR-2425, after board.mock.html was drawn). implemented is therefore the eighth status and the eighth column.

Order — implemented goes immediately after In Progress, before Planning. Both satisfy “between in_progress and in_review”; the fold below is what decides between them. Panel 1 — the fold, MEASURED

A column is w-72 (288px, shrink-0) in a gap-4 (16px) row (BoardColumn.tsx · BoardContainer.tsx), inside the shell’s lg:px-8 gutters beside a 240px rail (56px collapsed) — components/ui/AppLayout.tsx, app/(authed)/layout.tsx. So each column costs 304px and the count that fits is floor((content + 16) / 304). The table is measured, not derived: the panel-1 frame below is set to each content width in a Chromium render and every column’s getBoundingClientRect() is read against the frame’s box — the sliver figure is how much of the Implemented column is on screen at that width.

What gives: nothing, and that is the finding. The board is already a horizontally-scrolling row — six columns did not fit a laptop either — so the eighth column adds scroll distance, not a new failure mode. What the eighth column DOES change is which statuses a reader sees without scrolling, and that is a placement decision, not a layout one. At slot 4 Implemented is fully on screen from 1512px (or from 1440px with the rail collapsed) and shows a 63–223px sliver below that — enough to see that the column exists and has cards in it. At slot 5 it starts at x = 1216px and is off-screen at every laptop width in the table. The board’s own answers to a long board are unchanged and are enough: the rail collapses, the board scrolls and snaps (snap-x snap-proximity), and Epic 6’s board filter narrows it.

Panel 5 — CI at Implemented: what the board shows

A board card at Implemented shows nothing about CI, deliberately. BoardCardDto (lib/dto/boards.ts) carries no CI field, and adding one is a change to the board PROJECTION — outside MOTIR-2999’s stated scope boundary, which ends at “one card’s status lifecycle”. The board answers the operator’s question structurally: a card in Implemented is built and waiting on checks; a card in In Review is green.

The one thing this leaves unanswered is a RED build — MOTIR-2999 leaves such a card at implemented, so “checks running” and “checks failed” share a column. The verdict is one click away, on the item’s Development section, where the shipped CI pill already renders it (Running) alongside the per-head-sha comment applyCiStatusFeedback already posts. Surfacing failure ON the board is a board-projection card, named in the notes, and not this story’s.
