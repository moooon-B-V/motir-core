Bugs — where a project’s filed bugs land

The project-settings room that chooses the container Motir files new bugs under — the seeded one, any other epic, story or task, or the project root — and the rail entry that opens it. Story MOTIR-4927 · Subtask MOTIR-4933; implemented by MOTIR-4938.

It COMPOSES the settings-area chrome and the monitoring room’s layers, re-specifying neither, and reuses the shipped choice-card and Combobox grammars. What it decides is this room’s content: the three choices, the fallback when a chosen container has gone, the save states, and the door.

Panel 0 · The room as a project first finds it — the seeded container is the destination

Every project is born with a task titled Bugs and a destination pointing at it (MOTIR-4935). So the room opens on the first choice, naming the container it points at and linking to it — a destination a person cannot open is a destination they cannot check. Nothing is dirty, so Save changes is disabled, exactly as the Estimation card renders it.

Panel 1 · Choosing another container — the picker, open and filtered

The second choice reveals the shipped Combobox, composed the way ParentPicker composes it: searchable, each row a kind glyph, a title and the key. It offers only what can hold a bug — epics, stories and tasks, per the kind-parent matrix — and only from this project, grouped by kind so a project with hundreds of containers is still scannable. Picking one makes the card dirty.

Panel 2 · Project root, chosen — and the save in flight

The root is a named option with its own sentence, not a cleared field. Choosing it says what happens to the next bug in words a person can hold the product to. While the write is in flight both actions are disabled and the primary carries the spinner, so a second click cannot race the first.

Panel 4 · The chosen container was archived — the fallback, stated rather than hidden

The resolver files at the root when its container has gone (MOTIR-4937) — right, and invisible unless the room says so. So the room does not keep showing a live-looking name: the banner states what is happening now, and the stored choice is drawn struck through with an Archived pill, so a person can see both what they chose and why it is not in force. A DELETED container cannot draw this panel: its foreign key nulls the pointer, so the room reads Project root with nothing to explain — the notes record that limit.

Panel 5 · The access path — the door, drawn rather than described

Naming the route in prose is not drawing the entrance. The row below is the whole access path: Bugs in the Work group, last, directly under Components, with the lucide Bug mark. Grounded in PROJECT_SETTINGS_NAV’s own convention — the rail groups are General → Access → Work → Automation — and the argument for the group is the readers and writers of the value, not its resemblance to a neighbour.

Work, not General or Automation. The value decides WHERE in this project’s tree a kind of work item is created — the same axis as Fields and Components, which shape what a work item carries. It holds no third party’s credential, which is why Monitoring sits in General; and it does not configure how Motir behaves, which is what Automation holds. The monitor is one filer of many, so the room is not a section of the Monitoring room either.

root_selected Project root, selected, with its sentence. Never an empty control.
container_archived The warning banner saying bugs are going to the root, and the stored choice struck through with an Archived pill.
legacy_title_home Not a state a project in this room can show: the backfill gives every project a pointer before this room ships, so the transitional branch is never rendered.

What lands from this panel: one entry in PROJECT_SETTINGS_NAV — id: 'bugs', group: 'work' after components, icon: Bug, labelKey: 'nav.bugs', permission: 'project:administer' — and its route is MOTIR-4938’s to create. The rail, the command-palette deep link and the route↔registry totality test all follow from the one entry; no layout change.
