1 · A custom role joins as one more COLUMN (MOTIR-2257) — this is why the matrix is the right shape: a new role costs a column, not another full-height card. “Contractor” is the epic’s own motivating gap — may comment and attach but not transition — which none of the three built-ins can express (Viewer can’t comment, Member can edit). Note the affordance split: the built-in columns carry a LOCK, the custom column carries EDIT and DELETE. Built-in roles are not editable, so they have no edit control at all.

2 · Creating a role — the surface “Create role” opens, and the one thing this page lets anyone DO (the built-ins being immutable). A role is named, STARTS FROM a built-in base, and then adds to it: the base’s permissions arrive already checked and visually distinct (grey, “from Viewer”) from what the author adds on top (accent). Starting from a base rather than an empty grid is the GitHub custom-role pattern — it keeps a new role comprehensible instead of making the author derive eight booleans from nothing. The footer counts the result so the author sees what they are about to create. MOTIR-2257 builds this; MOTIR-2263 builds only panels 0/3.

3 · The catalog AT FULL SIZE — 32 permissions across 16 domains, the numbers MOTIR-2274 measured by walking every route. Only the 8 enforced role-gated keys render as matrix rows on the day this ships (the five groups expanded); the ten groups that are entirely planned collapse to a header with a pending count, and the sixteenth domain — public_request — is level-gated, so it renders in the Access-level card below the matrix exactly as in panels 0 and 2, never as a role column. That is the density lever this catalog actually needs: the length is in the NUMBER of groups, not in any one group — the largest is four rows — so collapsing GROUPS is right, and truncating rows inside one would fix a problem this catalog does not have. As MOTIR-2256 wires a domain its group expands in place; nothing about the layout changes.
