Roles & permissions — the role list, a role’s permissions, and creating one

Story MOTIR-2255 · Subtask MOTIR-2259 design asset — built from app/globals.css tokens. A DRILL-DOWN, not a matrix: screen 1 lists the roles one ROW each, screen 2 opens one role and shows its 28 permissions under 15 domain headings at full width. The matrix this replaces capped out at four roles — 902px of content, 132px a column, ~390px owed to the permission label — and custom roles are the whole point of MOTIR-2257. The marks are the model as it will BE, not today’s partial enforcement: Admin 28, Member 10, Viewer 2, over 28 role-gated keys, plus the three level-gated public-request grants in their own card. Built-in roles are IMMUTABLE (lock, no control); only a custom role carries Edit / Delete and a “Based on …” provenance. Panel 3 creates a role on a WHOLE PAGE with a sticky action bar. COMPOSES design/projects/settings-area.mock.html (rail + chrome), access-members.mock.html (role-chip grammar, the secondary Button) and details.mock.html (Input) — none is re-specified here. The one new primitive this asks for is a Checkbox, and only MOTIR-2257 needs it. See design-notes.md “Roles & permissions (MOTIR-2255)”.

0 · THE ROLE LIST — what “Roles & permissions” opens on, reached from the settings rail’s ACCESS group. One ROW per role, so the page grows with the number of roles a team invents rather than running out of width at four or five. FIVE roles are drawn on purpose: the matrix this replaces could not hold them — a 132px column each against a 902px content width, with ~400px owed to the permission label, ran out at four customs and wrapped every description to three lines before that. Each row carries the role’s purpose, its N of 28 — the coarse comparison the matrix used to give — and how many people hold it. MOTIR-2263 builds this screen.

Roles & permissions

What each role in motir can do. Workspace owners and admins always hold everything.

Create role
The three built-in roles can’t be changed — they’re what Motir guarantees. To fit a shape they don’t cover, create a role of your own.
Admin Built-in Runs the project. Every setting, every domain, and the work itself. 28 of 28 permissions 3 members
Member Built-in Does the work — edits items, comments, attaches, runs the planner. No project settings. 10 of 28 permissions 12 members
Viewer Built-in Reads the project and its reports. Changes nothing. 2 of 28 permissions 6 members
Contractor Custom Reads and discusses, but cannot change a work item — for people outside the team. 4 of 28 permissions 4 members
Reporter Custom A Contractor who also triages the request queue and reads generated plans. 6 of 28 permissions 9 members
Public requests
Granted by the project’s access level, not by a role — which is why they are not a role in the list above. Every visitor of a public project holds all three, signed in or not; nobody holds them on an open, limited or private project, a workspace owner included.
Access level
Submit requests Send a bug report or feature request into the triage queue.
Upvote requests Vote on a public request to signal demand for it.
Comment on requests Reply on a public request’s thread.
1 · A ROLE’S PERMISSIONS — drilled into Member, a built-in. The whole model at FULL WIDTH: 28 permissions under 15 domain headings, each on ONE line with its description beside it — the room the matrix could not spare. Held is a check, not-held a dash, and a not-held row stays fully legible because the page’s job is to show the whole model, not only the granted part. A built-in is immutable, so the head carries a LOCK and no control at all. MOTIR-2263 builds this screen.

Same screen as panel 1 with two additions, both admin-only: Edit and Delete, and a “Based on Viewer” chip. That chip is where the side-by-side comparison went: “Contractor is Viewer plus comments and attachments” is the relationship an admin actually needs, and it survives at any number of roles — where reading four columns at once did not. 3 · CREATING A ROLE — a whole page at /settings/project/roles/new, not a dialog. The revision before this authored a role in a 2165px modal inside a 900px viewport; a form this long is a page, and a page gives the permission list the same full width panels 1 and 2 have, so every description sits on one line. Name, then the base to start from — the base’s grants arrive ticked and greyed (from Viewer), what the author adds is accent-ticked. The action bar PINS to the bottom of the viewport with a running count, so the commit is never 1500px away from the tick that changed the answer — this panel renders inside a fixed-height scroll frame so you can SEE it pinned, with the rest of the list running behind it. (An earlier revision declared that bar sticky and it never pinned: two inherited ancestors are overflow: hidden, which kills position: sticky silently. See design-notes.) Editing a custom role is this same page with the values filled in — one surface, built once. MOTIR-2257 builds this.
