State D is a routine outcome, not an edge case. The poll is REAUDIT_POLL_MS (3000) × REAUDIT_POLL_TRIES (20) = exactly 60 seconds, and a first audit over five repos does not finish in one minute — so most first runs land here. Three consequences the consuming card must honour: (1) it renders INSIDE this empty state, NOT in the rose Card tint="rose" error strip where deepen.reauditPending goes today — a job that is still running is not an error, and colouring it as one teaches the user their audit failed. Left to right: the octocat + the repo's owner/name in mono (.coderef grammar) · then EITHER the grade chip OR an icon-and-word state · then the finding count as a neutral count-pill · then when it was audited. Selected is the highlight this asset already uses for a current row — --el-accent-on-surface border on --el-surface-soft — the same pair as .version.current and the Recommended .tool-rec card. No new selected-state vocabulary. Colour is never alone. The grade chip puts the hue in the TINT with --el-text-strong ink and repeats the grade LETTER and the percentage as text; the three non-graded states carry the colour on the ICON and the meaning in the WORD — the rule design/repository-set §15.6 fixed for its own per-repository rows. A failed read fails ONE row. MOTIR-2207 must degrade a rejected per-repo read to this row alone; the siblings stay readable and the page never falls into the whole-page rose error strip. That is why the fourth state exists at all — the card requires the behaviour, so the design owes it a drawn state. Rows are sibling buttons, never a listbox. A row carries a per-row action (“Try again”), and a role="listbox" of role="option" rows may not contain interactive children — the shipped SavedFilterDropdown failed the 6.2.6 axe sweep on exactly that (aria-required-children critical + nested-interactive serious). So: a role="group" wrapper, one <button> per row whose accessible name is the repo plus its state, the recovery as a SIBLING button, and the selected row marked aria-current — with its name in semibold, so selection is not colour-only for a sighted reader either.

The five rules the consuming card cannot re-decide. (1) The poll watches the repo whose report is on screen. reaudit() fires ONE POST /refresh (the MOTIR-2123 invariant) and then polls the SELECTED repo's audit surface for a new audit.id; if no repo is selected yet, it polls the first row. The selection does not move for the duration of the run, so the repo being waited on is always the repo being looked at. (2) The order is worst-first and it re-sorts only on a completed read — ascending conformancePct, then never-audited rows, with connected-repo order (owner asc, name asc) as the tiebreak and as the whole order before any audit exists. Selection is held by repoRef, never by index, so a re-sort can never move it. (3) Findings stay PER REPO and the pagination contract is untouched. nextOffset is an offset into ONE audit's findings; merging N lists would need N interleaved cursors, and no mirror does it. Switching repos RESETS the list — the new repo's first page, not an append onto the previous repo's. (4) The list is not drawn at all for a single-repo project — one row can neither be compared nor chosen, so N = 1 renders exactly what ships today. (5) The run SURVIVES the page (see the notes, §5b). Every deriving state above is RESUMED on mount from the job ids the trigger already returns, re-read through the shipped GET /api/ai/jobs/[jobId] — never from component state, which is gone on the next mount. Until that resumption resolves, no re-audit trigger renders at all, or the page offers a returning user a duplicate fan-out on work already in flight. That signal is MOTIR-2223's deliverable and MOTIR-2207 is blocked_by it.

“You can leave this page — the audit keeps running” is a promise, and half of it was free. The JOB half is already true: the trigger POSTs once, motir-ai persists each job, and the browser's poll is only an observer — navigating away cancels nothing. The PAGE half was not: reauditing, pollExhausted and the returned ReauditResultDTO are all component state, so a user who took the copy at its word came back to “No audit for this code yet” and a primary button meaning “nothing has happened yet” — on a project mid-run. Rule (5) is what makes the sentence true on both halves.

The action is the row's LAST element, after the timestamp — one trailing slot, one control, never two. The row keeps Panel 7 §6's anatomy exactly; this appends to it. An unavailable row gets NO audit trigger — only its shipped “Try again”. The read FAILED, so nothing on screen knows whether that repo has a report; offering “Audit this repo” there would spend a derivation to fix what may be a display error. Re-READ first — it is free, and it tells you which state the row is really in. This is also what keeps the two actions from ever sitting one pixel apart: the free recovery and the paid trigger are mutually exclusive per row, so a mis-click between them is not possible rather than merely unlikely. Weight encodes price, and the words differ. btn-secondary (bordered) for Audit this repo — the one thing worth doing on a row with no report; btn-ghost for Re-audit and Try again — the rarer need and the free recovery. The trigger is a SIBLING of the row's select button, exactly as onRetry already is — never nested inside it. No confirmation dialog, and the reason is on this page rather than in taste. The shipped whole-project “Re-audit now” fires on ONE click with no confirm — and it is the expensive action, deriving every connected repo. Every trigger this panel adds costs strictly LESS than that button already costs unconfirmed, so gating the cheaper action while the dearer one stays ungated would teach exactly the wrong lesson about which press is worth pausing over. What replaces a dialog: the row flips to Deriving… immediately, so the press is visibly acknowledged; the trigger is then REMOVED from that row, so it cannot be pressed twice; and MOTIR-2223's durable in-flight record means even a reload cannot produce a duplicate run. If a confirm is ever wanted, it belongs on the whole-set button FIRST — that is a separate decision about a control this panel does not touch.
