The roadmap canvas you come back to

Four refinements to the SHIPPED /roadmap surface, drawn as one board because they all move the same chrome: the level-addressable URL, the full-fold canvas frame, the collapsible Dependencies panel, and the ARRIVAL VIEW a level is first drawn at. Every canvas, node card and legend below is the app’s own rendered markup, dumped from ProjectRoadmapCanvas / WorkItemNode / RoadmapView and laid out by the shipped deterministicLayout — not a redraw. Every number is measured in Chromium, not derived. This asset COMPOSES design/roadmap/roadmap.mock.html and design/roadmap/edges.mock.html; it redesigns neither.

A level arrives at a readable scale

The real WorkItemNode at NODE_W×NODE_H = 280×124, rendered in Chromium at deviceScaleFactor: 1 and read. Type sizes are the card’s own, multiplied by the scale: identifier font-mono text-xs (12), title text-sm (14), status chip text-[11px].

THE FLOOR IS 0.80, and it is derived, not chosen. The card’s smallest authored type size is the 11 px status chip, so the rule is: the TITLE never renders smaller than the smallest type the card itself authors. 14 × s ≥ 11 ⇒ s ≥ 0.786, rounded up to a clean 0.80. At 0.80 the title is 11.2 px, the identifier 9.6 px and the chip 8.8 px, and the strip above shows all three still resolve at 1×. The code card takes this number; it does not re-derive it.

UNCHANGED — a small level (this story’s own five subtasks) fits whole at 1.040, above the floor, so it is fitted exactly as today.

  • The rule, in one sentence a code card can implement with no second decision: fit the level when fitView’s scale is at or above 0.80; otherwise arrive at 0.80, centred on the level’s focal card.
  • Centring is PER AXIS, and this is the clause that stops the arrival looking wrong. On an axis where the level FITS at the floor, centre the level’s BOUNDS; on an axis where it does not, centre the focal CARD. The root level is 800 px wide at 0.80 in a 1136 px box, so it is centred horizontally and only the vertical follows the frontier — centring the card on both axes parks a first-column card in the middle and leaves a third of the canvas empty.
  • The focal ladder is the shipped one — the here frontier first, then the first ready node, then the level’s first node in layout order. It is the same priority the LOCATE control already uses (ProjectRoadmapCanvas.tsx, locateActionable), so the canvas gains no second notion of “the node that matters”.
  • Centring is centerOn, not a second transform — the geometry module already exposes exactly this (lib/planning/canvasGeometry.ts), and the arrival is centerOn(focalRect, viewport, 0.80).
  • The “you are here” ring is the card’s own — the accent border + map-pin pill WorkItemNode already draws for here. Nothing new is painted to make the centring read as deliberate.
  • It is an ARRIVAL, not a floor on zoom. MIN_SCALE = 0.3 is untouched: a reader who wants the whole eighteen-epic level still zooms out to it.

Panel 4

The URL remembers the level

A behaviour panel with no new pixels — and it belongs in the asset because it is what the surface PROMISES. Today the drill level lives in mount-time useState, so a reload, a shared link and browser Back all land you back at the project root.

●app.motir.co/roadmap

The project ROOT level. The canonical URL — the param is omitted, exactly as ?scope= omits project.

●app.motir.co/roadmap?item=MOTIR-1234

A DRILLED level. The param names the item whose CHILDREN are the level in view — you land inside MOTIR-1234, which is where a drill leaves you, not on a level that merely contains it.

●app.motir.co/roadmap?scope=sprint&item=MOTIR-1234

Composes with the shipped scope param (MOTIR-1541). Two independent view-state params on one route.

  • Both fallbacks are SILENT, and land at the root. An item that does not resolve, or that the viewer cannot browse, falls back to the root level — the same silent catch /planning already uses for its ?item= anchor (app/(planning)/planning/page.tsx). So does an item outside the active-sprint slice when scope=sprint. No error state, no toast: a stale link is not a failure, it is a level that no longer exists.
  • An item with NO CHILDREN opens its PARENT’s level, with that node SELECTED. A drill can never write one — the canvas only drills a drillable node — but a hand-typed or hand-edited link can, and “the level whose children are none” is an empty canvas that reads as a failed load. A parentless childless item falls back to the root, per the rule above. The selection is the canvas’s shipped selectedId, not a new highlight.
  • The trail is seeded, not guessed. The server resolves the anchor’s ancestor chain with workItemsService.getWorkItemWithAncestors and hands it to the canvas’s shipped initialTrail prop, so the breadcrumb reads identically to a hand-drilled one.
  • A drill WRITES the URL with a push, not a replace. Back must return to the previous level — MOTIR-1549 exists because the scope toggle once used a replace and Back stopped restoring it. The write is shallow (lib/navigation/shallowUrl.ts): the level is already in the browser and the server has nothing to re-answer.
  • Back/forward MOVES the level. The URL is the source of truth after mount, which the canvas does not do today — hence the sibling card’s onLevelChange + controlled trail, both opt-in and both defaulting to today’s behaviour for the other four consumers.
  • Scale and pan on a URL restore are the ARRIVAL, not a saved viewport. A restored level is an arrival like any other and takes Panel 2’s rule; nothing persists a pan.

Planning flags

⚠ What this pass surfaced that no card in MOTIR-3833 owns

  • The 3-column layout wastes the canvas’s WIDTH, and that is what forces the arrival scale down. deterministicLayout is fixed at COLS = 3, so an 18-node level is a 1000×1324 world box — taller than it is wide — inside a canvas that is 1136×620 and wider than it is tall. fitView is therefore bound by HEIGHT at every viewport measured, and today’s arrival leaves 30–50% of the horizontal room empty (visible in Panel 2’s TODAY frame). A column count that responded to the viewport would raise the fit scale before any of this story’s changes did. No card in MOTIR-3833 owns it, and it is outside the story’s scope boundary as written; it is a follow-up, not a silent widening of the arrival card.
  • min-h-[28rem] still makes /roadmap scroll on a short window. The full-fold card removes the symptom at 1366×768 (the computed height becomes 488, so the floor stops binding), but the floor is untouched, so a window shorter than ~608 px of usable height still scrolls the one signed-in surface the shell promises never scrolls (app/(authed)/layout.tsx’s h-dvh overflow-hidden root). Whether a canvas should have a minimum height at all is a decision nobody has made.
  • The Reset-layout / orb overlap is a SHIPPED defect, not one this story introduces — measured at 1366×768 today, the button overlaps the orb by 19 px, because the min-h floor already pushes the canvas past the band the shell reserved. The full-fold card’s lift fixes it as a side effect; recording it here so it is not re-discovered as a regression of this story.
  • Nothing persists a canvas PAN or ZOOM, and this asset deliberately does not add it. Panel 4 settles that a URL restore is an ARRIVAL — the level is addressable, the viewport is not. If a per-level saved viewport is ever wanted, it is its own story with its own storage decision, not a clause in the arrival rule.
