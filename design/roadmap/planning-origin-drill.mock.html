Why the unconditional “Complete” is wrong. The badge is a claim about the journey's output, but its only evidence is a marker that records the journey ran — so on a project whose pre-plan wrote nothing it asserts four documents that do not exist. Not an error state: Idea and Plan keep their checks (the marker is set on first plan approve/materialize, so it genuinely attests both), the strip still reads as provenance, and the neutral chip reports a fact rather than flagging a fault. And it never blocks first paint: the produced set is the only thing the badge needs, so the card paints its chip-less state immediately and upgrades when the read lands — it can never claim “Complete” before it knows. Drillability needs no read at all: drilling is what reveals whether documents exist.
E Drilling a journey that produced NOTHING — still worth landing on the card is always drillable

The phase card drills whether or not documents exist, so this level has to say something on its own. It does: the four stations in their shipped upcoming face name the journey's shape, and none of them offers a View. No empty-state illustration, no error, no new component — the honest reading is “this is what a pre-plan produces, and this project has none of it”.

F The keyboard path — both hops, on the canvas's own affordances no new canvas contract, no new key handling

Because both hops use the canvas's OWN action slot rather than a control drawn inside a card, the keyboard path is the one the canvas already ships and this design adds no key handling at all. PlanningCanvas wraps every node in a tabIndex={0} div whose Enter / Space selects it, and the Open › / View buttons that selection reveals are real <button>s inside that wrapper, so Tab reaches them.

① the phase card Tab to the node · Enter selects it — the canvas's outline --el-accent ring.
② drill Tab onto Open › · Enter drills. Breadcrumb + Back appear; focus lands on the new level.
③ a station Tab through the stations · Enter selects. A not-produced station reveals no View.
④ the doc Tab onto View · Enter opens TierDocModal. Focus moves into the dialog; Esc returns it.
This is the affordance argument, not just an accessibility note. A control drawn INSIDE a card would have had to fight the wrapper — its keydown bubbles into a handler that calls preventDefault(), which cancels a nested button's implicit click — and a press on it would have had to stopPropagation to escape the canvas's drag/select gesture. Routing both hops through the canvas's own action slot means none of that exists to get wrong, and notes.html #139 (a bare click on a canvas card only ever selects) holds by construction rather than by care.
