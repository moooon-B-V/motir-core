Decision What it means for the code card (MOTIR-1807)
Breadcrumb alone carries the skipped level No hint banner, no tell on the crumb, no new roadmap.canvas.* string, and therefore no messages/en.json + zh.json addition. The treatment is information-preserving on its own: the crumb names the ancestor and is one click from restoring it, and the rung-1 precedent (VS Code explorer.compactFolders) adds no explanation either. A banner would also make the arrival a special mode, which is the opposite of this story's position.
The crumb label becomes identifier · title Required. The shipped label is the bare identifier (workItemLevel.tsx — crumbLabel: item.identifier). On a manual drill that is enough, because the user just read the card they clicked. On an arrival nobody clicked, MOTIR-809 references the skipped level without naming it — so "the breadcrumb alone carries it" would be false. One-line change: crumbLabel: `${item.identifier} · ${item.title}`. It applies to manual and auto crumbs identically, so no special mode is introduced and MOTIR-1807's "crumb label identical to a hand-drilled one" criterion still holds exactly.
Room for the longer label Crumb's max-w-[12rem] → max-w-[18rem], and the overlay's max-w-[min(36rem,…)] → max-w-[min(44rem,…)]. The shipped truncate + the existing native title={label} tooltip stay as the overflow answer — a three-crumb chain still ellipsises, by design.
Nothing else changes Back control, separators, aria-current="page", the aria-label={t('breadcrumb')} nav, the focus ring, tokens: all shipped, all untouched.

Both skipped ancestors are crumbs, in descent order — the same order a two-click manual drill would produce. The chain stops the moment a level is not "exactly one drillable node", which is what makes the arrival land where the plan actually branches. With three crumbs the overlay is at its widest: the last crumb ellipsises and the shipped title tooltip carries the full string. That is the intended overflow answer — not a second line, and not a smaller font.

Level shape Descend? Why
Exactly 1 node, drillable YES No choice to make; the work is one level down. Panels A / C / D.
Exactly 1 node, not drillable NO Nothing beneath it — descending would land on an empty level. Panel E2.
2 or more nodes NO There is a real branch; the choice is the user's. Panel E1.
Empty level NO The shipped emptyRootTitle / emptyDrilled empty states own this; nothing to descend into.
The user navigated UP to this level NO An explicit navigation is never fought. Panel F.

What happens next Re-descend? Why
The user just sits here / pans / zooms NO They asked to see this level. Showing one card is the honest answer to that ask.
The user hits the header refresh control (MOTIR-1540) NO Refresh re-reads the CURRENT level. Re-descending would make Refresh feel like it lost their place — the same in-place contract roadmap-refresh.mock.html panel 2 already draws.
The user explicitly drills into the card YES An explicit drill re-arms the behaviour — a chain below it still compacts.
The user switches scope (project ↔ sprint) YES A scope switch is a fresh arrival, not a navigation within the current tree.

No visual difference marks the suppressed state. The resting level is an ordinary root level — the same one card, the same drill chevron, no breadcrumb. Suppression is behaviour, not chrome: drawing a badge for it would tell the user about an internal flag they never set.
