The OAuth consent screen — connect an app to Motir

MOTIR-6980 for MOTIR-6985. The page an MCP client’s browser redirect lands on: which app is asking and where it returns, one workspace, all projects or one, the grant in the token picker’s own columns and words, Approve / Deny — and every state around it. Multi-panel; review each. Copy and per-element tokens are in design-notes.md § OAuth consent.

Panel 0 — the entrance · nobody navigates here inside Motir — the client’s browser redirect IS the door

The person added Motir’s MCP and asked to authenticate. Claude Code discovered Motir’s sign-in from the MCP’s 401, registered itself, and opened the system browser at the authorize endpoint.

Connecting an app

Claude Code — you’ll pick a workspace and approve next.

The shipped sign-in form — Google · passkey · email, then password or 2FA — unchanged and not redrawn (design/auth/ 01–12, two-factor-challenge, passkey-sign-in).

Only the account you sign in as can approve this — and only its workspaces can be picked.

The hand-off

The authorize endpoint, finding no session, sends the browser to the sign-in page (Better-Auth’s loginPage). The ONLY change to sign-in is the carried banner — the same IdeaCarried the CLI hand-off uses (“Connecting the CLI”). It names the app, never the workspace: nothing about the account is known yet.

sign in as usual — password, Google, passkey, and the 2FA challenge if the account has it
the browser returns to the authorize URL, whole query encoded into next
authorize re-validates and redirects to the consent page (Panel 1)

⚠ The whole authorize query rides in next, the /device lesson: a bounce that keeps only the pathname drops state, code_challenge and resource, and the client gets nothing back.

Panel 7 — invalid request · an error PAGE that does not redirect — no Approve, no Deny
app.motir.co/oauth/error?error=invalid_request&error_description=redirect_uri
Motir

This connection request can’t be used

Nothing was connected, and you haven’t been sent anywhere.

It asked to send you back to http://evil.example/cb, an address it never registered with Motir.

Go back to the app and start connecting again. If this keeps happening, the app is set up wrong — tell whoever makes it, and quote invalid_request · redirect_uri.

You can close this tab.

The request The callout sentence Quoted code
Unknown client_id The app isn’t registered with Motir, or its registration has expired. invalid_client
redirect_uri not registered It asked to send you back to <host>, an address it never registered with Motir. invalid_request · redirect_uri
PKCE missing, or not S256 It left out a security check Motir requires on every connection. invalid_request · code_challenge
resource is not this MCP It asked for access to something other than Motir’s MCP server. invalid_target · resource

It does NOT redirect because it cannot be sure where to: an unregistered redirect_uri is exactly an attacker’s address. Whether the PKCE and resource rows also land here, or redirect with the RFC error once the redirect is proven good, is MOTIR-6982’s call — this page is drawn for every row it DOES receive. The host is named in words; the code is quoted for the app’s maker, not for the reader.

The redirect back

Approve records the connection, then the page shows this state and immediately sends the browser to the app’s registered redirect with the code. What the person sees next is the app’s own page, not Motir’s.

localhost:53682/callback?code=…&state=…
Claude Code: “Authentication successful. You can close this window.” — then /mcp shows motir connected
claude.ai/api/mcp/auth_callback?code=…&state=…
claude.ai: the Motir connector reads “Connected”

If the app’s page never loads (a loopback listener that already closed), the tab stays on the Motir card at left — which is why it says the connection is made and the tab can be closed, rather than “redirecting…” forever.
