1 The Changelog tab, sixth in the public sub-bar, after Roadmap — the two answer adjacent questions (what is coming / what shipped), so they sit together. Route /p/<identifier>/changelog. Built by 8.9.4.
2 The sidebar Links row. The external links.changelog row is REPLACED, not joined — it loses the ↗ glyph because it no longer leaves the site. A project that never set the external URL gains the row for the first time, since the native changelog always exists. Built by 8.9.5.
3 The Follow button, in the public top bar to the LEFT of Sign in — it is the project's affordance, not the account's, so it leads the account CTAs rather than hiding behind them. It is present for a signed-out viewer too (Panel D2 draws what pressing it does). Built by 8.9.5.
Why all three and not one. The changelog is reachable from a tab (a person browsing), from the sidebar (a person reading the README), and the feed is reachable with no page visit at all. Drawing only the tab would leave 8.9.5 to invent the other two — the gap the design-reference rule exists to close.
(B) The CHANGELOG page at /p/<identifier>/changelog, populated — the 8.9.4 surface. Entries are DERIVED from done-transitions (8.9.1 §2), so nothing here is authored: there is no draft, no publish button and no per-entry edit. Grouped by DAY, newest first, 20 per page. Each entry carries only the public-safe columns plus the shipped date and the ancestor-epic chip (§3) — no assignee, no estimate, no story points, and no work TYPE.

What an entry is, and what it is not. An entry appears the moment a work item enters a shipped status and is dated by that transition — so a project that uses the tracker gets a changelog for free, and one that does not gets an honest empty one. An item that is reopened LEAVES the stream and returns, higher, when it ships again; a cancelled item never appears at all, because "resolved" and "shipped" are not the same statement (8.9.1 §2, AMENDMENT 2). A private epic (6.14) is absent — and, unlike the tree, so is its own row: there is no placeholder entry in a stream.

Why the email field comes FIRST when signed out. The visitor arrived from a link and has no Motir account; asking them to make one before they may hear about the thing they just decided they were interested in inverts the funnel this page exists to feed. The account route is offered second, with the one honest advantage it has (no confirmation step). This is the single place Motir deviates from Canny, which requires an account — 8.9.1's Context carries the justification.

E4 is a whole affordance removed, not a disabled one. Where the deployment configured no transactional-email backend there is no digest to offer, so the two email tiers are absent and the popover collapses to the feed — the same shape the DSN-unset monitoring path takes. A greyed-out checkbox with a tooltip would advertise a capability the operator cannot turn on from this page. RSS and the changelog itself never depend on email, which is the whole cloud-vs-self-host split for this story.
