Take it over — move your repositories to your own GitHub

The room behind two shipped doors. The repo-set step promises "It's yours — move it to your own GitHub whenever you want" and the billing panel's exhausted state offers Move repositories. Neither leads anywhere yet: the shipped OwnershipPromise deliberately renders its door unlinked — "a link to a 404 is a worse broken promise than no link, and a surface that draws a door owes a real entrance" (RepositorySetStep.tsx). This asset draws the entrance those doors earn.

The flow is GROUNDED, not invented. Every state below is MOTIR-711's saga (requested → transfer_pending → awaiting_reinstall → done, plus failed, per ROW); every cost line is ci-minutes-allowance.md §D's binding copy rule; the re-enable-then-transfer ordering is §G; the no-op for a row the user already owns is ADR project-repository-set.md §3. Nothing here decides anything those did not.

Drawn against SHIPPED reality. RepositoryRow, IdentityHeader and GrantRow all ship as code and were RENDERED from their own source + the real compiled globals.css before anything was drawn; the two host mocks were rendered with Playwright. Every row, identity block and grant row below mirrors those renders element for element (notes.html #73). Nothing shipped is redrawn.

Panel 0 · The doors — three entrances, one room, drawn IN their host surfaces

A design that names a route in prose has not drawn an access path, so each door is rendered as the real affordance inside a repro of the surface that owns it, haloed. Two of the three already ship as design assets and are composed here, not redrawn. The third is the room's own permanent door: the project-settings rail.

Why the settings rail is not an invention. The room mounts at /settings/project/repositories, and lib/settings/projectSettingsNav.ts is a REGISTRY whose own comment says "a later admin story mounts its page by ADDING an entry here — no layout change" — and whose totality test pairs every settings/project/**/page.tsx 1:1 with a registry entry. A page on disk with no entry FAILS that test, so the nav row is a consequence of the mount, not an extra surface. It is also what makes the flow re-enterable: a transfer left half-finished is picked up from a door that is always there, never only from a step the user has already left.

Panel 2 · Pick the target — and the three states the picker really has

⚠️ The org list is a live call, so it has states — drawn, not assumed. GithubIdentity stores exactly one login, the user's PERSONAL githubLogin (prisma/schema.prisma, read at rung 2). There is no stored org list anywhere, so the organizations are a GET /user/orgs with the user's token — which can be slow and can fail. An instantly-populated list would be a drawing of a system that does not exist. The personal account is always available and is never behind that call, so a failed org lookup degrades to a working picker rather than a blocked flow.

The decision is a modal; the STATE is not. Everything in panels 2–3 is transient — pick, read the costs, confirm — so it lives in a Modal. Everything in panels 4–7 outlives it, survives a reload and must be re-promptable, so it lives on the ROW. That split is what keeps transfer_pending from being drawn as a spinner in a dialog nobody left open.

Panel 3 · The costs, stated before the user commits — never "one click"

ci-minutes-allowance.md §D is binding and its wording is quoted, not paraphrased: the option is framed as "GitHub bills you for Actions directly from then on, and Motir stops charging CI credits", and it states its real costs — a GitHub account you own, an asynchronous transfer you must accept on GitHub, and a re-install of the Motir App on the new owner so dispatch keeps working. Never "one click." The three costs are therefore the confirm step's SUBSTANCE, not fine print under it: each is a line with its own glyph, and the second and third are named as things the user will have to go and DO.

What it does NOT cost is stated too. §G decides that the transfer re-enables Actions unconditionally, so a user moving a repository because CI is paused is told the CI comes back — otherwise the honest cost list reads as pure loss and the option the ADR designed as a real second answer looks like a punishment.

Panel 4 · transfer_pending — a place, not a spinner

MOTIR-711: "the call is asynchronous, and for a personal-account target the new owner must accept on GitHub, so transfer_pending is a real state resolved by a webhook or a poll, not a spinner." Drawn accordingly: the row keeps this state across reloads, sessions and days; it says what the user must go and do, and where; and it offers the way back to GitHub every time it is seen. A spinner would promise that waiting in front of it accomplishes something — it does not, because the next move is the user's, on GitHub.

The tint is --el-warning-surface, and that is a deliberate third register. Mint means settled and Motir's; sky means yours; peach means waiting on you. No state is carried by colour alone — every one below pairs an icon with a word (finding #35).

Panel 5 · awaiting_reinstall — the hand-off that keeps the loop alive

The repository is the user's now, and this is the state where Motir is honest about what it costs them: a GitHub App installation is account-scoped, so the grant did not travel with the repository, and until it is re-established dispatch and the code-graph index stop working. The row says exactly that — the consequence, not just the chore.

Repository selection happens on GitHub's screen and is never faked in-app. The hand-off composes the SHIPPED install path — githubAppInstallUrl() / githubInstallationManageUrl(), whose own source comment says the install grant "happens ENTIRELY on GitHub; Motir only links OUT to it" — and the panel beside it REUSES the shipped GrantRow and IdentityHeader from gitSettingsPrimitives.tsx rather than redrawing them. The user is told the one thing GitHub's screen will not tell them: which repository to tick.

Panel 6 · done — transferred, its new owner shown, the loop alive

The row lands in the SAME shape a connect-existing row has always had — sky, Yours — because that is now what it is. Nothing on this surface distinguishes "yours because you brought it" from "yours because you took it over", and that is the point of the promise the flow exists to keep. The only extra line is the billing consequence, which is the one thing that genuinely changed for the user.

MOTIR-711 does not mark it done on the transfer alone — reaching done requires a new GithubInstallation under the new owner. So this row is proof the loop survived the hand-off, not just proof the repository moved.

Panel 7 · failed and recovery — three ways to be stuck, none of them wedged

MOTIR-711 requires that "an unaccepted transfer or an unfinished re-install is re-promptable, and re-running any step is a no-op." The three are drawn separately because they are genuinely different: only ONE of them is a failure. An unaccepted transfer and an unfinished re-install are the flow working correctly and waiting on a human — they keep their own peach waiting register and their resume affordance, and they are never tinted as errors. Only a request GitHub refused is red.

Panel 8 · One row of three — the set mid-move, with the others untouched and working

MOTIR-711's per-ROW rule, drawn at set scale, because it is the property most easily lost in implementation: "taking over one row of three is legitimate and must not wedge the others." The web row is mid-hand-off; the api row is still Motir-hosted, still running, and still offers its own move; the shared row was never Motir's. Three ownerships and three states, in one set, all legal at once — and the header's summary counts the truth instead of implying the project is "moving".
