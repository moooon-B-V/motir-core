Where should your code live? — the step at plan approval

MOTIR-1778 · Story MOTIR-1775. The step that gives an approved plan somewhere for its code to live. Motir hosts it by default, in one sentence, because the person answering is a founder and not a developer — and the repository detail (names, roles, per-row state) exists only for the user who explicitly says they already have code. Grounded in the accepted ADR docs/decisions/project-repository-set.md; the surface it lands in was rendered from a production build before anything was drawn.

Panel 0 · The access path — where the step sits, and what happens on completion

The step is the second half of the shipped approve action, in the shipped surface — not a floating panel and not a gate. Pressing Approve — add 24 items to your backlog materializes the plan (the items are in the backlog before this step is answered, so nothing here can cost the user their plan) and derives the repo set. The step then takes the CANVAS pane of the same box; the review rail is reused untouched, now showing Approved. On completion the rail's outcome gains one plain line — "Your code is ready" — and never a repository count or name.

The set is a durable property of the project (ADR §4.4), so the step is re-enterable — but the DEFAULT path has nothing to come back for, because Motir finishes it. The door back in exists for the two cases that need it: setup didn't finish (panel 2c), and the user later decides to use their own GitHub. The permanent home for both is the code-context surface (MOTIR-1764 / Story MOTIR-1754) — not drawn here, and not this card's to design.

Panel 1 · The default — one sentence, one action, and a small way out

The whole step, for everyone who has not said otherwise. No repository name, no role, no account, no count, no rows, no table, no "seeded from" — a founder is told what happens to their code and what it costs them (nothing, and it stays theirs). The only branch is a single quiet I already have code, sized like the exception it is. This is the notes.html #151 rule applied: derive it, use it, and don't ask a non-technical user to curate a developer artifact.

Panel 1b · Both cardinalities — the same screen whether the plan needs one repository or three

The card's central problem, answered by removing the question rather than by styling it two ways. The ADR's model is unchanged — the set still has as many rows as the architecture decides (§0.1), and a plan that separates a backend still gets its own repository — but the cardinality is not the user's business, so it is not on screen. These two renders are identical pixels; only what Motir did behind them differs. ADR §6 already reserved exactly this: "the one-question feel is a property of the PRESENTATION … never of a second branch in the model."

Panel 2 · The default path has three states — working, ready, and couldn't finish

The ADR's six per-row states are the model; this path renders only what the user can act on. creating → "Setting up your code…", created → "Your code is ready", and failed → one plain sentence with one button. There is no per-repository progress, no repository name in the error and no GitHub status code — those belong to the technical path (panel 5). proposed, connected and skipped cannot occur here: nothing is proposed for approval, nothing is adopted, and there is nothing to decline.

Panel 3 · "I already have code" — the small way out, and the hand-off 7.10 owns

Choosing this is how a user self-identifies as technical — and only after it does any repository vocabulary appear. It is one short confirmation, then the shipped GitHub connect flow (mirrored below from app/(authed)/settings/workspace/github/page.tsx): two grants, identity then install. This design does not redraw those screens — 7.10 owns them — and nothing on the default path sends a user to GitHub before they ask for it.

Panel 4 · The technical path — once connected, what the plan needs and where each part lives

Everything below is behind the "I already have code" door. The user has connected their own GitHub, so repository vocabulary is now theirs to read: one row per part the plan needs, each row saying whether Motir creates it in their account or connects one they already have.

This is where "Add a repository" vs "Use an existing repository" stopped being ambiguous. They were siblings on one line, which made them read as alternatives — they are not. They now live at different levels: per row, a Segmented answers where does THIS part live — Create for me or Use one of mine; at set level, Add a repository only ever means the plan needs a part Motir didn't infer. One asks where; the other asks how many.

Panel 5 · The technical path's per-row states — and the partial outcome

The ADR §4.1 machine, drawn at row scale, on this path only. Rows are independent — a row's state is carried by the row, so one spinner or one failure leaves its siblings alone (§4.2), and nothing is rolled back. State is carried by an icon + a word + a token fill, never colour alone (finding #35) and never a dashed border, which the canvas already owns for a different meaning. No state is terminal: failed and skipped keep every forward path, at this visit or a later one. A state pill is deliberately not used on a tinted row — Pill severity="danger" and --el-danger-surface are the same token value, so it would be invisible; the tint goes on the row and the state is named in text beside its icon.
