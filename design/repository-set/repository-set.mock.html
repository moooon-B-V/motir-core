Panel 0 · The access path — where the step sits, and what happens on completion

The step is the second half of the shipped approve action, in the shipped surface — not a floating panel and not a gate. Pressing Approve — add 24 items to your backlog materializes the plan (the items are in the backlog before this step is answered, so a skipped or failed row can never cost the user their plan) and proposes the repo set. The step then takes the CANVAS pane of the same box; the review rail is reused untouched, now showing Approved. Completing the step adds the repositories line to that rail's outcome — and while any row is unresolved, the rail keeps the door back in, so no state is a dead end.

Panel 1 · ONE row — the start-fresh case: one question, one answer

The common case, and the one the design is judged on. There is no table chrome, no count, no "1 of 1", no reorder grip and no per-row ⋯ menu — the set-level affordances that only make sense once there is something to compare. The row is a single labelled field; the name is acme-booking with no role suffix (ADR §1.4) and the role is not chipped, because with one repository there is nothing to distinguish it from. What it is seeded from is stated plainly underneath. The quiet secondary is still reachable — Use an existing repository sits beside Add a repository as plain text rather than behind a per-row ⋯ menu, because a one-row set has nothing to disambiguate.

Panel 3 · Every per-row state from the ADR's machine — each with its forward path

The six states of ADR §4.1, drawn at row scale. Rows are independent: a row's state is carried by the row, never by the step, so one row's spinner or failure leaves its siblings alone (§4.2), and nothing is rolled back. State is carried by an icon + a word + a token fill — never colour alone (finding #35) and never a dashed or dotted border, which the canvas already owns for a different meaning. No state is terminal: failed and skipped both keep every forward path, at this visit or a later one.

Panel 4 · The PARTIAL state — created + failed + skipped in one set, and the step still finishes

The state a real user hits, drawn as a first-class picture rather than left out of a happy-path mock. Row 1 was created, row 2 failed, row 3 was skipped — and the step is completable (ADR §4.3): the summary counts the truth, the primary action is Finish setup, and nothing pretends the failed row succeeded. Each row keeps its own recoveries, here and on any later visit.

Panel 5 · The no-GitHub path — the same rows, under Motir's organization, claimable

Not a different journey and not a wizard: the same step, the same rows, the same primary action. Only the set-level target line changes, and one callout explains what "Motir owns these" means and how to undo it (ADR §3.3 / §3.4). There is no GitHub prompt anywhere on this path — connecting an account is an offer in quiet secondary type, and it hands off to the shipped Git settings pane (rendered above; 7.10 owns those screens, so they are pointed at, never redrawn). Ownership is decided once for the whole set — a set is never half in the user's account and half in Motir's (§3.5).

Panel 6 · Use an existing repository — the quiet secondary, and how a monorepo collapses the set to one row

Create is the only prominent action per row; adopting a repository you already have is the quiet alternative, on the row's own menu. It is also the monorepo escape hatch (ADR §6): one repository for everything is a one-row set whose row is connected rather than created — the same model, no second code path. Switching a row to this state swaps the name field for the shipped Combobox over the repositories Motir can already see, and offers to drop the rows the monorepo makes redundant.
