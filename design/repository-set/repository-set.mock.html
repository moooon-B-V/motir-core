Where should your code live? — the step at plan approval

MOTIR-1778 · Story MOTIR-1775 · v5: MOTIR-5011 · Story MOTIR-5010. The step that gives an approved plan somewhere for its code to live. Motir hosts it — always, for everyone, in one sentence, because the person answering is a founder and not a developer. Because those repositories are private and under Motir's org, Motir invites the user to them (MOTIR-1900) — and since v5 that invitation is sent, not offered: the step reports which account it went to instead of asking for one. The repository question itself now belongs to ONBOARDING, which is the only place a project without a repository can be (MOTIR-4753), so the technical path this asset used to draw has left for design/onboarding-migrate/. Grounded in the accepted ADR docs/decisions/project-repository-set.md and its 2026-07-30 amendment (MOTIR-1893, repos are always Motir-owned); the surface it lands in was rendered from a production build before anything was drawn.

Panel numbers 3–7 are deliberately absent. They drew the access PROMPT and the technical path, both of which v5 removes; the numbers are not reused, so every existing citation of "panel 4" or "panel 6" still resolves to the thing that left rather than to something new wearing its number. §0.1 of the notes says where each one went.

Panel 0 · The access path — where the step sits, and what happens on completion

The step is the second half of the shipped approve action, in the shipped surface — not a floating panel and not a gate. Pressing Approve — add 24 items to your backlog materializes the plan (the items are in the backlog before this step is answered, so nothing here can cost the user their plan) and derives the repo set. The step then takes the CANVAS pane of the same box; the review rail is reused untouched, now showing Approved. On completion the rail's outcome gains one plain line — "Your code is ready" — and never a repository count or name.

v5 · the main line is back to THREE frames, and the one that left is the question. Every repository is still created under Motir's org and is still private (ADR §3 amendment), so a user still cannot clone their own code until Motir invites them as a collaborator — which needs their GitHub login. What changed is where Motir gets it: onboarding. MOTIR-4753's routing verdict refuses continue outright when a project has no repository (motir-ai src/llm/onboardingRouting.ts:210), so only a project that came through onboarding ever reaches this step — and connecting is onboarding's own connect step, drawn in design/onboarding-migrate/ Panel 1. The invitation is therefore sent at establish and frame 3 reports it. Asking here was asking a question the product had already been answered.

Panel 1 · The default — one sentence, one action, and a small way out

The whole step, for everyone who has not said otherwise. No repository name, no role, no account, no count, no rows, no table, no "seeded from" — a founder is told what happens to their code and what it costs them (nothing, and it stays theirs). v5: there is no branch at all. The quiet repositorySet.iHaveCode door led to the technical path, and the technical path has left for onboarding — which is where a user who already has code was always going to be sent, because a project with no repository cannot be planned at all (MOTIR-4753). One statement, one action, and nothing else on the screen. This is the notes.html #151 rule applied: derive it, use it, and don't ask a non-technical user to curate a developer artifact.

Panel 1b · Both cardinalities — the same screen whether the plan needs one repository or three

The card's central problem, answered by removing the question rather than by styling it two ways. Panel 2 · The default path has three states — working, ready (in THREE arms since v7), and couldn't finish

The ADR's six per-row states are the model; this path renders only what the user can act on. creating → "Setting up your code…", created → "Your code is ready", and failed → one plain sentence with one button. There is no per-repository progress, no repository name in the error and no GitHub status code — and, since v5, no technical path for them to belong to either. proposed, connected and skipped cannot occur here: nothing is proposed for approval, nothing is adopted, and there is nothing to decline. The ownership promise sits on the state itself, not in a footnote — it is the sentence a reviewer must be able to SEE in MOTIR-1785's acceptance video, so it is a line of its own with the door to MOTIR-711's transfer beside it.

v5 · created STOPS ASKING, and that is the whole of this revision. Until v4 this state's forward action was repositorySet.connectGithub — named by its KEY throughout this asset, and nowhere by its English string, so a grep of that string over this file returns zero and MOTIR-5011's criterion is machine-checkable rather than asserted. It was a question the product had already been answered, because a project only reaches plan approval by way of onboarding, and connecting a repository is onboarding's own connect step (MOTIR-4753's routing verdict refuses continue outright when the project has no repository). So the invitation is now SENT at establish, as MOTIR-1900 already specified it — "a side effect after commit, degrading gracefully" — and this state REPORTS it. THREE arms since v7, and all three are drawn: something was sent (A), there is no account to invite (B), or Motir had one and GitHub refused (C). A report is not a silent surface — arm A still offers Use a different account, because a mechanism that shows you which account got access and gives you no way to correct it is worse than one that asks. What left is the ASK for the identity, not the ability to fix it.

Arm B's words are the RAIL's words, by construction. PlanDetail.codeOutcomeOf already resolves a created row nobody has been invited to as needs_access, and PlanReviewRail renders that as "Finish setting up access" (repositorySet.outcomeNeedsAccess). The panel's door reuses that key rather than restating the string, so the two cannot drift apart in a later edit. Its explanatory sentence is likewise the shipped notInvitedDetail, which is also what /settings/project/code-access says about the same state (settings.codeAccess.state.notInvitedSelf).

v7 · arm C, and why arm B could not keep answering for it. Arm B's guard is !login || !anyInvited — a two-disjunct SHAPE test — while its caption said "no connected identity". A GitHub refusal satisfies the second disjunct: nothing is stamped on one (grantAccess counts a row-level refusal and never throws; deriveAccessState(null) is not_invited), so the panel told a user whose account Motir knows that Motir does not know it. The three arms are now predicates, in this order: B when view.githubLogin === null; C when it is non-null and every INVITABLE row (state === 'created') is not_invited; A otherwise. The connected login is what makes C sufficient — since v5 the invitation is sent at establish, so a set that reached created while Motir held an identity has already had its invitation attempted. The severity ruling is untouched: an invitation failure never fails a row, so C keeps the success line, the promise, arm B's ink and icon, and arm B's door — /settings/project/code-access, which branches not_invited on the DTO's own reason and offers Invite for exactly this state.

Panel 8 · What this becomes when the hosted agent ships — re-read for v5: the variant's AXIS changed, and v5 draws 8b

v5 draws 8b, and 8a is kept as the record of what this panel used to be about. Panel 8's two arms turned on whether the access STEP is primary — 8a, today, every user continues into the connect prompt; 8b, after Epic 9, that prompt becomes the quiet option. v5 deletes the prompt from both arms, so that axis no longer separates anything: the step reports and the primary is Go to my backlog in both. What survives of the distinction is a different and smaller question — whether the REPORT is worth showing at all once the hosted agent pushes for the user and nobody needs the repository on their machine.

The answer, decided here rather than left open: 8b is the drawn state, and the report STAYS after Epic 9. The invitation is sent whether or not the user ever clones anything, so suppressing the line would mean a user who has been granted admin on a private repository is never told — and the ownership promise directly above it ("move it to your own GitHub whenever you want") is a promise they cannot act on without knowing which account holds the keys. A report costs one line and answers a question the product raised itself; the earlier reading, that it is an aside for developers, was a property of the PROMPT, not of the fact.

8a still has a home — and it is §0.1's revision history, NOT an artboard. A reader who arrives from MOTIR-1782 or MOTIR-1900 and finds the button those cards specify missing needs to know it was superseded and why, which is exactly what a revision-history row is for. It must not be a DRAWN panel: a mock is the layout source of truth, and a board that still draws a retired control is a specification for putting it back — which is how this surface came to ask a question the product had already answered. So the artboard below is 8b alone, and 8a survives as a record in prose.

Drawn side by side because the point of v5 is that these two frames are now nearly the same frame. Before v5, Epic 9 was going to demote a primary button; after v5 there is no button to demote, and the only thing the hosted agent changes is one line of helper copy about what the user does next. That is the test v5 was aiming at: a step that REPORTS does not have a pre-Epic-9 shape and a post-Epic-9 shape, so MOTIR-5015 does not need to keep anything swappable — which is what §7 asked MOTIR-1782 to preserve and what this revision retires.

Panel 9 · A SETTLED set draws no step — and a MIXED set scopes what the step claims

Until v6 this asset had no state for a project whose repository set arrived already settled — every row connected, because the repositories are the organisation's and onboarding connected them. It had something stronger and worse: panel 2's table declared that population impossible ("connected … cannot occur"), while the shipped surface rendered the step for it on every approval, because the gate in app/(authed)/plans/[id]/page.tsx is a row COUNT (rows.length > 0) and reads neither state nor seedSource. Since MOTIR-4753 a project cannot be planned at all without a repository, so this is not an edge case — it is every BYOK project, on every approval.

The step does exactly one of two things — ASK Motir to establish code, or REPORT what it established — so a row Motir will not create and did not create gives it neither. The band is drawn iff the set holds at least one row Motir ESTABLISHES: state in proposed / creating / created / failed. Not set.ownership, which is null until the step decides and so is null for exactly this population; and not codeOutcomeOf() === 'ready', which counts created as settled too and so cannot tell a set Motir just built (which DOES owe a report) from one that arrived settled (which does not). state decides whether the step APPEARS; seedSource decides what it may CLAIM.

No band, and no residue — not a collapsed one-liner, not an empty seam, not a hairline where the step used to be. The reader is told exactly one thing about their code, by the review rail, which already says it: "Your code is ready" under "Added 24 items to your backlog". Nothing is added to the rail either. The tempting addition is one line naming where the code lives, and it is refused for the reason v2 was refused — it is a technical fact the reader did not ask for, in a rail whose job is the DECISION's outcome, and a project's repositories have a durable home already at /settings/project/repositories. The cost, stated plainly: a user approving a plan on a settled project is told nothing NEW about their code at all. That is correct — nothing new happened to it.

The mixed frame differs from panel 1 in exactly two strings, and in nothing else. title → titleMixed ("Motir will host the new code") and promise → promiseMixed ("Motir keeps the code it hosts safe and private"). Both edits are SCOPE, not information: the panel still names no repository, no role, no account, no count and no rows, so nothing about the set's composition reaches the reader, and a project with an all-Motir set sees panel 1 byte for byte. That is the test a scope edit has to pass — and it is why the fix is not a second paragraph explaining the split, which would be v2's mistake in miniature. The honest home for "which repositories does this project have" is the Repositories room, which already splits its sections on isOrganizationSeedSource — the same predicate, rendered where a reader went looking for it.

And the h2 is UNCONDITIONAL in shipped code today, which is why this is a design decision and not a copy tweak. The title element sits outside every state branch, so "Motir will host your code" is asserted in working, ready and failed alike, for every set. For the settled population that is simply false; for a mixed set it is half true. Both are the same missing scope, and a builder who fixes only the gate leaves the sentence standing — so §2's v6 table reads the four rendered elements one by one, and three of them are false of a repository the organisation owns.
