Panel 1 · The room — /settings/project/code-access, an owner looking at the team

The matrix is N members × M repositories and access is granted per repository, so the surface has to choose an axis. It is member-primary: one row per invitable member, with the repository SET named once at the top and the per-repo breakdown available on the row. The reason is that the axis carrying the DECISIONS is the member — eligibility (Q1) and a connected identity (Q3) are properties of a person and settle every repository at once — while the repository axis varies only the invitation mechanics. It also puts the surface in the same person-first grammar as the pane beside it. A set of three is the shape, not the exception: the row summarises across the set and only opens when the repositories disagree.

Panel 3 · The second dimension — a row opened, per repository

The summary line is a roll-up across the set, and it is honest about disagreement rather than averaging it away: Has access only when every repository is accepted, Couldn't invite the moment one failed, otherwise the count. A row opens by default when the repositories disagree and stays closed when they agree — so the three-repo case reads as one line, and the case that actually needs three lines gets them. The per-repo list is where Q2's permission lives too: push for a teammate, admin for the person who approved the plan.

A connected row — a repository the team already owned and granted Motir — carries no invitation line at all and is left out of the count, for the reason needsCollaboratorInvite gives in code: inviting somebody to a repository they already own is at best a no-op. The same is true of a skipped row, which is why a partial set needs no special case.

Panel 5 · Empty · loading · partial · refused — the four states that aren't the happy one

None of these is a dead end, and none of them is an error page. The pane always renders; what changes is how much it can honestly say. Refused is the one worth reading twice: GitHub turning an invitation down must never fail the repository row, so the failure is stated per person, the repositories stay created, and the count at the top counts what is TRUE rather than what was attempted.
