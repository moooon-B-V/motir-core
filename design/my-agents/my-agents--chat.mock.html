MY AGENTS, delta — the Chat tab — /my-agents?agent=<id>&tab=chat

MOTIR-6863 · MOTIR-7011. The agent panel’s second tab: a conversation with the agent’s own coding agent — a transcript with its tool calls, a prompt box pinned below, and the agent’s past sessions — modelled on Claude Code’s cloud session view. It amends design/my-agents/my-agents--panel.mock.html (MOTIR-6937), whose tab track held only Terminal; that asset is not changed.

It composes, it does not redraw. The list cards, the header, the sign-in line, the tab track, the strips and the faces are the panel design’s markup and styles, copied. Most panels below show the panel from its tab track down; the header above it is unchanged.

Every state is the decision’s. The supported set, the subscription refusal, the frames, the seven event kinds, Stop, the per-agent limit, the session list and 4411 are docs/decisions/agent-chat.md (MOTIR-7010) Q1–Q8. Vocabulary: an agent, its coding agent, a chat, a session, a turn.

1THE TAB IN THE TRACK — Chat beside Terminal: active, inactive and disabled.

The second tab in the approved track. The panel design drew the track holding only Terminal and said the chat story adds Chat beside it; this is that tab, with a MessageSquare glyph. The active tab is the approved .tabOn; the inactive one is the same box on the track with secondary ink. Switching tabs changes nothing else: the header, the sign-in line and the connection word stay where the panel design put them, and the word describes the tab that is open.

Which tab opens. An agent opens on Terminal, as it ships. The open tab is kept in the address as &tab=chat (written with shallowPush: the chat renders itself, the server has nothing to answer), so a reload returns to the chat.

A new chat (agent-chat.md Q4 open with no session) is an empty transcript with one line that says what the chat is and is not: it works in the terminal’s ~/workspace (Q3), each turn is the CLI headless (Q3), and turns run under the sandbox’s auto-approve flags, so the agent does not ask before it acts (Q3, and What this does NOT decide: no approval prompt is built).

Disabled is aider’s, and only aider’s (Q1: the supported set is Claude Code, Codex, OpenCode, kimi and goose). The tab is drawn from CHAT_PROFILES (Q8) without connecting: aria-disabled, a Ban glyph, secondary ink, and the reason in a tooltip on hover and keyboard focus, tied by aria-describedby. Terminal is untouched. Panel 7 draws it in the whole panel.

2THE TRANSCRIPT — a prompt, the tool calls folded away, a reply streaming, then complete.

One shape for every coding agent (Q5): the tab draws the seven event kinds and nothing else. A user event is the developer’s prompt, right-aligned on the surface ground. text is the reply as plain prose on the card, no bubble; deltas with one id join into one paragraph, and while they arrive the paragraph ends in an accent caret. A tool_call is one collapsed row in the order it happened (panel 3 opens them).

While a turn runs a quiet line under the transcript says Claude Code is working…, the connection word stays Live, and Send becomes Stop (panel 5). Claude Code and goose stream word by word; Codex, OpenCode and kimi send each message whole (Q1, Granularity differs), so on those the caret is never seen — the paragraph lands complete. The tab does not pretend otherwise.

Scroll. The transcript fills the tab between the bar and the prompt box, down to the bottom of the viewport (the terminal’s rule), scrolls inside itself, and stays pinned to the latest event unless the reader scrolls up — then the approved Jump to latest appears instead of yanking them down. What never appears: token counts, cost and thinking blocks (Q5 drops them; Q10).

3THE TOOL-CALL ROWS — each kind collapsed and expanded: a read, an edit with its diff, an edit with a path only, a command with clipped output, any other tool, a failure.

A row names the act, then the thing. The four kinds of Q5, each with its glyph: Read + the file path (FileText); Edit + the path (FilePen); Ran + the command (SquareTerminal); and for other, the tool’s own name and title with no verb (Wrench). At the right end, the one fact worth a glance: lines read, +added −removed, the exit code, Running… while the tool_result has not arrived.

Collapsed by default, one click (or Enter/Space) opens it — the head is a disclosure button with aria-expanded. The body is the tool_result on the code ground: a read’s content, a command’s output, an edit’s unified diff with added and removed lines on the diff tints. An edit the stream reports by path only (Codex’s file_change, Q5) opens to one line saying so, rather than an empty box.

Clipped output (truncated: true, over 64 KiB, Q5) opens with a note above it — the start is what was cut, so the note sits where the missing part would be. A failed tool call (ok: false) takes the danger border and Failed · exit 1 in danger-on-surface ink with a CircleX; it is drawn open here, but it is not opened for the reader — the turn goes on after it.

4HOW A TURN ENDS — completed, stopped, failed; and the two rows that do not end one.

Every turn ends in one marker, written by the runner, never by an adapter (Q5, Q6): a thin rule with the reason in its middle. Turn complete (completed) with a success check. Stopped (stopped — the story’s “the transcript records that it was stopped”) with a square, and one line under it: the text already streamed stays, cut where it was (Q6). Turn failed (failed) in danger-on-surface ink, with its code said in words under it.

The Q2 backstop reads as a failed turn with the subscription code: if Claude Code’s own first line shows it is running on a subscription after the gate let the turn through, the runner ends the turn at once and the marker says why. The next prompt meets the refusal face (panel 7).

Two quiet rows that never end a turn. An error event (a retry, a denied tool, Q5) is an inline notice on the warning ground, and the turn carries on under it. An other event — a line with a type nobody mapped — is one secondary line naming it, and nothing else (its content is never shown or logged, Q10).

5THE PROMPT BOX — idle, typing, sending, running (Stop), disabled; and the two refusals it can meet.

Pinned to the bottom of the tab, under the transcript. A multi-line text box (Enter sends, Shift+Enter is a new line; the hint says so) and one button. Idle: the box is empty and Send is off; it becomes the primary button as soon as there is text. Typing: the box grows to about eight lines, then scrolls. Sending: from the prompt frame to the first event of the turn, the button reads Sending… and the text has already moved into the transcript. Running: the button is Stop (Q6: SIGINT, then SIGKILL after 5 s), and the box stays editable, so the next prompt can be written while the agent works and sent once the turn has ended (sending it earlier meets turn_running, below).

Disabled whenever the chat is not connected (waking, connecting, reconnecting, lost, panel 8): the box is on the disabled input ground, keeps whatever was typed, and the hint says typing comes back on reconnect.

The two refusals are a strip directly above the box, and neither empties it, so nothing typed is lost. turn_running (Q6: one running turn per agent, not per session) names why on the warning ground. too_large (a prompt over 64 KiB, Q4) on the rose ground, with the way around it. A prompt is text only — no attachments, images or slash commands (Q4, What this does NOT decide).

6THE SESSION LIST — newest first, empty, at its bound of 50; a resumed session with its history, one whose history is unavailable, and taken over.

Sessions in the chat bar opens a popover listing the agent’s sessions from the CLI’s own store (Q7): newest first by last activity, each row the session’s title — the CLI’s own, or the first prompt cut to 120 characters, one line with an ellipsis — and when it was last active in the app’s relative time. The open session is marked (aria-current, the option-active ground). New chat heads the list. A row resumes that session in the tab (Q4 open with session). Sessions started in the terminal are listed too, and not told apart (Q7).

Empty says where sessions come from. At the bound — the list carries at most 50 (Q7) — the foot says older sessions are not listed and are still in the coding agent’s own history, so a missing one is not mistaken for a lost one. Nothing about a session is copied to Motir (Q10), so there is no search and no count beyond the 50.

A resumed session shows its title in the bar with a Resumed chip and its earlier turns drawn exactly like live ones, before any live event (Q4 history). When the history was cut to its newest 256 KiB (truncated) a note heads it. When the adapter answers unavailable (Q7), the session opens with no earlier turns drawn and one note saying the agent still has them. Taken over (Q6: a later open of the same session elsewhere wins) is the terminal’s strip, reworded: the turn keeps running there, and Use it here re-opens it in this tab.

7WHEN THE AGENT CAN’T CHAT — aider’s disabled tab, Claude Code on a subscription, not signed in, and an image with no chat server (4411).

Aider (Q1, unsupported): the Chat tab is disabled in the track and the panel stays on Terminal, untouched. The reason is the tooltip of panel 1 — Aider has no machine-readable output for a chat to follow — and it is known before anything connects (CHAT_PROFILES, Q8).

Claude Code on a Claude subscription (Q2, option b) — a required state, and for most Claude Code users the one they will see. The tab is enabled, because only the agent knows its sign-in: the server’s hello carries subscription_signin, and the chat body becomes one face — a Lock glyph, the title, the Q2 sentence in full with the way forward (an Anthropic API key or a cloud provider), and Open Terminal. The Terminal tab sits beside it in the track, live and usable, and the sign-in line in the header still says Signed in to Claude Code: the terminal on a subscription is the carve-out case and is not affected. No prompt box is drawn, so nothing can be typed into a chat that cannot run. Motir offers no way to set a key from here (Q2: the user configures their own, as Claude Code documents).

Not signed in (Q4 not_signed_in, Q6: the terminal’s own check) is a refusal at the moment of sending: nothing runs and nothing moves into the transcript, the prompt stays in the box, and the strip points at the terminal, where the vendor’s own flow signs in (Q11 — the chat never starts a sign-in). The header’s sign-in line already says the same, with the command. When the sign-in lands (the signin frame), the strip goes, and Send sends the kept prompt. Can’t be checked is let through (Q6), so kimi and goose never see this strip.

No chat server (close 4411, Q8): an agent made before this story. The same register as the panel design’s image-too-old face — the Package glyph, what happened, that moving to the newer image is on its way, what works until then — and no date and no button. The connection word is Unavailable; the terminal tab is unaffected.

8THE CONNECTION — waking, connecting, reconnecting and lost, in the terminal tab’s treatment.

The chat is its own socket (Q4: /v1/chat, a ticket for the chat channel), so it has its own connection word at the strip’s right end, the approved words and dots. The faces and strips are the terminal tab’s, reworded for a chat: waking is the panel design’s waking face (opening a hibernated agent wakes it, no second click); connecting is the centred line; reconnecting is the sky strip, the transcript dimmed and the prompt box disabled with its text kept; lost, after the same reconnect window, is the rose strip with Reconnect, and the machine-not-answering variant (4502) reuses the panel’s own sentence.

A dropped socket does not stop a turn (Q6), and every strip says so. On reconnect the tab re-opens the same session and receives its history, then the running turn’s kept events (up to 256 KiB), then live ones — so the transcript redraws and carries on, and a turn that ended meanwhile shows its end marker. A stale ticket (4401) and not_running have no words, exactly as on the terminal.
