This is its own asset, and it draws the target — not a migration. WHERE the switcher lives: a 44px PANE HEADER at the very top of the canvas pane, above the establish band. The pane had no header at all — PlanningWorkspace's canvas slot is filled edge to edge — so one had to be decided rather than found. It goes at the TOP of the pane, not between the band and the body, for one reason: it governs the BODY, and the band is not part of the body. Part VI decided the establish step STACKS above the canvas rather than replacing it; putting the switcher under the band would make the band read as chrome belonging to one of the two views. Above both, it is what it is — the pane's own control bar. The band keeps its position relative to the body it precedes, and nothing inside the step changes.

The right end of that bar is Part IX's, and it is drawn here so the pane's chrome is decided ONCE. The dashed Show changes block is a PLACEHOLDER carrying Part IX's mark: its behaviour, its treatment and its states are Part IX's to specify, and Part VIII specifies only that it sits at the bar's right end, opposite the switcher. Leaving it undrawn is how a pane ends up with two control bars.

The row is the shipped ChildList row, with the plan's own op language on top. Kind glyph (IssueTypeIcon, its --el-type-* hue), identifier, title, a facts line, and a right-hand chip — the same grammar the Children list uses, so a reader who has read one has read the other. The op chip is panel B's own add / modify / remove vocabulary, unchanged; the list introduces no fourth language for the same three facts.

An add has NO KEY, and the list says so rather than leaving a gap. identifier is null until approve materializes it, so the slot the key occupies reads no key yet in the faint monospace the key itself uses. An empty slot in a column of keys reads as a missing value; this reads as the fact it is.

A modify shows its diff as TWO-LINE TEXT, per changed field — and that is deliberately NOT the canvas's inline overlay. The canvas's overlay answers this node is changing inside a node card ~280px wide: it is a signal. The list answers changing to WHAT, at the full width of the pane, for a reader deciding whether to approve. So the list is the only surface that spells a change out, the canvas is the only surface that marks a node, and neither is built twice. A field whose new value is a BODY (description, explanation) is named and not quoted — a rewritten description is not a diff a review list can carry, and a truncated one is worse than a pointer.

The remove disposition is DECIDED: a THIRD SECTION, not a footnote and not a silent drop. A plan holds three ops. A list showing two of them under a row whose item count counts all three is a surface that contradicts itself, and the count is on the row that got the reader here. The request named the cards it adds and the cards it updates because those are the two a plan usually holds — not as an enumeration of what a list may show. So the list renders Adds · Updates · Archives, each section appearing only when it is non-empty, and the plan's item count keeps its whole-plan scope because the list now covers the whole plan. An archived row takes panel B's own remove treatment — struck title, muted ink, the archive chip — and nothing red or dashed (archive is reversible; red-hatch stays reserved for the canvas's cross-story dependency signal).

A DECIDED plan's list is a RECORD, and it is reconciled with Part VI in one sentence: Part VI decided the canvas pane holds the record of what was accepted rather than a set of proposals, and the list is the same pane's other body, so it says the same thing in the same tense — Created / Applied / Archived rather than + add / change / archive, and every row that HAS a key now shows one. A declined plan's list keeps the proposal tense and adds no outcome chip: nothing happened to those cards.

· the valve MOTIR-3189 opened, and the control that reaches it
plansService.declinePlan accepts a generating plan and records decisionReason: 'discarded' (MOTIR-3189). PlanReviewRail renders its Decline button with disabled={!planned} and the hint reviewLocked. So the valve exists and has no door, and the two plans this story was written about had been sitting at generating for the better part of a day with a control that could have ended them, greyed out.

The confirm

Discard this plan?

It has 3 proposals so far and is still being written. Discarding ends it now and keeps the proposals as a record — nothing in your backlog changes, and nothing is created.

DISCARD, not Decline — the copy is a decision. The rail's declineCta says Decline, and declining is what you do to a finished proposal you have read. A plan that never finished is not being rejected on its merits; it is being ENDED. Plan.decisionReason already tells the two apart on the row (discarded vs reviewed, MOTIR-3189), and the button is where a reader learns which one they are doing.

It CONFIRMS, and the confirm names the proposals. Approve confirms when items are stale, and this is the sharper case: the action is irreversible from this surface, the plan is still moving, and the number of proposals it has already written is the one fact that tells the reader what they are throwing away. The confirm reuses the shipped Modal at size="sm" — the same one the stale-approve confirm uses — and its primary carries the same word as the control that opened it.

The reviewLocked hint is REPLACED, not removed. It said “Review & Approve unlock when generation completes”, which was true of both buttons and is now true of one. The replacement keeps that promise for Approve and states what the second control does, because a hint under two buttons that describes only one is how the live control reads as disabled too.

Who may press it is UNCHANGED. ai:decide_plan gates the discard exactly as it gates approve; a reader without it sees the same rail without the control, as they do today.
