The plan timeline carrying CONTENT events

The review rail's timeline can say four things today, all of them status transitions, and it can name only one of a plan's three parties — the decider. This asset draws what it looks like once it also carries the acts that changed the plan's CONTENT: an append, a deepen, an edit, each named to the party that made it.

It draws rows on the timeline that already renders. It does not redraw the plan review canvas, the proposal peek, the approve / decline controls, the staleness summary or the decided outcome, and it introduces no colour that is not already in the palette.

The list already carries two kinds of row

An event that HAPPENED takes an --el-accent dot and two lines; the one PENDING row takes an --el-border-strong dot, one line and no timestamp. That vocabulary is shipped, and Panel 2 joins it rather than inventing a third.

The agent vocabulary is already on this surface

Four rows above the timeline, an agent-written plan renders as a bot glyph, a harness and a model. The timeline does not need a second way of naming an agent — it needs this one, compressed to a row.

The band the new rows land in

528.5px of fixed chrome, 44px per row. So the rail begins to scroll when its height falls below 528.5 + 44N — which is why Panel 4's collapse rule is load-bearing rather than tidy.

2

The same plan, with its content events — ONE sequence, ONE row grammar

The decision: content events are not a second kind of row. They join the same ordered list, in the same two-line box, with the same dot, and the ROW'S OWN WORDING is what tells a reader which kind it is — a lifecycle row names a state the plan reached (Plan ready, Approved), a content row names an act somebody performed on it (5 proposals appended). A second treatment would ask a reader to learn a distinction that pays nothing: nobody filters this list and nothing acts differently on the two halves. What genuinely differs is VOLUME, and volume is answered by Panel 4's collapse, not by a second dot.

4

The collapse rule, and what a row does NOT show

Consecutive rows of the same kind, by the same actor, with nothing between them, are ONE row. The count is over the acts; the timestamp becomes a span. Collapse is on kind + actor + adjacency and never on a time window — a window merges two agents' work, adjacency cannot. And a collapsed run never swallows a different kind: a Plan ready, an approve or a decline always breaks a run, so no decision is ever hidden inside a count.

Why it is not cosmetic

A titles-first pass is one skeleton append plus one edit PER proposal, so ten proposals is eleven rows before anything a reader cares about. At 44px a row, the uncollapsed list on the left is 440px of timeline — enough, on a short window, to push the Approve button out of view on a plan nobody has looked at yet.

The diff a row shows AT REST: a count, and nothing else

Not the fields, and not the values. Measured: Estimate and story points changed · Claude Code is 56px — two fields already spill to a second line, and a deepen touches up to nine. A row that names its fields is a row that cannot hold them.

And nothing expands

No disclosure triangle, no drawer, no hover card in this revision. What a proposal currently SAYS is already two surfaces away and better rendered there — the list view and the proposal read view. The timeline's job is what MOVED and who moved it.

5

The legacy plan — nothing is drawn, and that is the drawing

A plan created before this ships renders exactly today's timeline. No no changes recorded line, no dimmed placeholder, no explanatory caption. Every plan in the product today is this plan, so an empty state here would put a permanent apology on the whole back catalogue — and the absence is not a gap: nothing was recorded because nothing recorded it. The rail already has one row for the thing that IS outstanding, and it is the pending row.

The assertion this earns

A plan whose revision set is empty produces byte-for-byte today's event list. That is a test the read card can write against an empty table, and it is the state every existing plan is in.

One shipped detail the read card must change

Today each row is keyed key={ev.kind}, which is unique only because each lifecycle kind occurs at most once. Feeding the shipped rail eight events with a repeated kind renders all eight and logs "Encountered two children with the same key" — measured, not inferred. Content rows repeat, so the key becomes the event's own identity.

And one ink correction it inherits

The shipped actor clause is --el-text-muted on --el-surface — 4.17:1, below AA. Every actor on this board is --el-text-secondary (6.24:1), which is what the row that gains an actor on most of its lines should carry.

6

The access path — no new door

The timeline is reached exactly as it is today: the left nav's Plans entry → a plan row in the list → the plan detail at /plans/{id}, where the rail is the right-hand pane and History is its second section, under the header and above the approve gate. This asset adds no route, no tab, no control and no entry affordance — it adds rows to a section a reader already lands on. That is the whole of the access path, and it is stated here rather than drawn because there is no new door to draw.
