The plan canvas at arrival, and Show changes

The plan-detail canvas’s BEHAVIOUR — what it does when it opens, and one control it does not have. Three decisions: the LEVEL it arrives at (a proposed container counts), the breadcrumb crumb for a parent that does not exist yet, and a Show changes toggle that lights every card the plan touches on the level in view and pushes the rest back.

This is its own asset, and it draws no new surface. /plans/[id] is reached exactly as Part I §5 draws it — the left-nav Plans entry, then a row — and this Part adds no entrance. It does not amend plans-surface.mock.html, which records the moment MOTIR-843 / 2985 / 3074 / 3082 / 3159 drew; the canvas, its node cards and the three op languages are composed as that asset draws them.

The five cards the plan is actually about, on the level they land on, with the proposed story named in the breadcrumb. The epic is one Back away — the direction a reader can discover.
The rule, in words: the canvas opens on the level the plan most FILLS — counting proposals under PROPOSED containers as well as committed ones. Today arrivalLevel counts an item only when it has a committed parent (if (!item.parentNodeId || !item.parentIdentifier) continue), and getPlanReview sets parentIdentifier to null for an intra-plan planItem: parent — deliberately, and correctly, because such a parent is drawn on the canvas rather than in the breadcrumb. So the count discards exactly the items the null describes, and the plan above scores ONE edge (story → epic) instead of five. parentNodeId is populated for those items; it is the field to count.

What this changes, and what it does not. A plan of pure roots still opens at the top level. A plan whose proposals all sit under ONE committed parent still opens there. What moves is the plan that proposes a container AND its contents — which is the shape an agent-authored skeleton produces almost every time.

The TIE-BREAK is the DEEPER level, and it is now reachable. One story under an epic plus one subtask under that story is 1–1. The shipped code keeps whichever level the Map yielded first, which is an accident rather than a decision. Prefer the deeper one: a reviewer wants to land where the work is, and the shallower level is one Back away while the deeper one is a drill they must first discover. Depth is the length of the arrival trail, which the same pass already builds.

The DEGRADE — an archived ancestor, above a proposed parent
Roadmap New · Payout reconciliation

An archived or hard-deleted ancestor yields parentTrail: [] beside a non-null parentNodeId, and the shipped code already degrades to a single synthesised crumb. When the parent is ITSELF proposed there is no committed chain to synthesise from at all — so the trail is the canvas's own ROOT crumb (roadmap.canvas.breadcrumbRoot, the label bug MOTIR-3152 fixed) plus the proposed crumb. The canvas never arrives with no breadcrumb, and Back always leads somewhere real.

The crumb keeps the committed grammar and substitutes the SLOT, not the shape. A committed crumb is KEY · Title (workItemCrumbLabel); a proposed one is New · Title, with the word New where the key would be. That is a TEXT distinction first — which is what the rule against carrying meaning in colour alone asks for — with the accent ink, the dashed border and the + glyph as the second and third channels.

Why not a key. identifier is null on an un-materialized add by construction, and a placeholder key (MOTIR-?, #new-3) would assert a work item that does not exist — on the one surface whose entire promise is that nothing is real until approve.

The treatment is not new and must not be. ProjectRoadmapCanvas's node wrapper already rings a selected or search-matched node (ring-2 ring-(--el-accent) ring-offset-2 ring-offset-(--el-surface-soft)) and already dims everything outside the connected set (opacity-35). Show changes applies that same pair to a SET — one ring value, one dim value, one vocabulary.

The set is every proposal on the level in view, whatever its op — add, modify and remove alike. A modify or remove shares its node id with the committed card it targets, so the ring lands ON that card rather than beside it. The op languages stay exactly as Part I §3 panel B draws them: they say WHICH change this is, and the emphasis says THAT there is one. They are orthogonal, and neither is an alternative to the other.

The dim is the shipped 35%, not lower. A committed sibling is on this canvas for a reason — “seeing the company a proposed card will keep is most of what ‘is this the right place for it?’ means” (planLevel.tsx) — so dimming it to invisibility would defeat the level the emphasis exists to read.

The count names what is NOT here, and offers no way to reach it. The canvas is per-level; a plan spread over three parents has most of itself off-screen. The control reads 3 of 11 whenever the level holds fewer than the plan's total, and stops there. The way to the other eight is Part VIII's LIST, which is the whole reason that body exists — a second navigation affordance here would be a worse answer to the same question, in the pane that already has the better one.

A selection is a momentary act; the toggle is a mode, and a mode should survive one.

Part VI made this pane a RECORD after the decision, with its own accepted / declined node treatments. “What did this plan change?” is a better question after approve than before — the cards are real now and sit among neighbours that were always there — so the control stays and its label moves to the past tense. On a DECLINED plan it stays too, reading the same, because the record is of what the plan would have changed and the reader is asking the same thing.

a11y and motion. The toggle is a real button carrying aria-pressed, so its state is announced rather than inferred from its fill; when disabled it carries the reason as its accessible description. The emphasis is never colour alone — a ringed node also carries its own op badge, which is TEXT (add / change / archive), and the dim is a second non-hue channel. And because turning this on changes the opacity of most of the screen at once, the transition is dropped entirely under prefers-reduced-motion: reduce: the state changes instantly rather than fading.
