One line, FULL-BLEED, and that is the whole non-blocking mechanism. It is the shipped SettingsBanner — role="status", --el-callout-bg fill, py-3, text-sm — spanning the workspace edge to edge and sitting FLUSH against the top bar, with no gutter and no gap. There is no heading, no repo list, no card, no glyph column: a person who does not care reads past it in one glance and keeps planning, which is what makes a dismiss unnecessary rather than merely optional.

The strip is between the workspace's top bar and its panes — PlanningWorkspaceHost's canvas column already has exactly this seam (the Close · project name bar, then a min-h-0 flex-1 canvas). Full-width above BOTH panes rather than inside the canvas, so it never scrolls away with the tree and never narrows the conversation. It is full-bleed and flush: no gutter either side, no gap above, square corners, and a --el-border-soft bottom rule — the SAME rule the top bar already draws, so the banner reads as one more band of workspace chrome rather than a floating object placed on the plan. The ONE deviation from SettingsBanner is the dropped --radius-card, which follows from the full bleed: a rounded corner only reads as a corner when there is margin outside it.

B · NO DISMISS · it is present EVERY time the workspace opens, until the audits exist

There is no × and no dismissed state. The banner renders on every visit to /planning for as long as a connected repository has no audit, and it disappears the moment that stops being true — because the condition, not a preference, is what it reads. The remedy IS the dismissal: audit the repositories and the banner is gone; that is one click away, in the link it already carries.

Why a dismiss would be wrong here, not merely unnecessary. A dismiss on a SELF-CLEARING signal only ever hides a true statement. The state it would persist — “this person has seen it” — has no bearing on whether the plans being made right now are being made without the repository's recorded standards, which is the fact the line reports. And it removes a whole class of bug. A persisted dismissal keyed on anything coarser than the exact repo set would silence a DIFFERENT problem later: connect a new repository next month and the banner about IT is suppressed by a click from today. That is precisely the complexity ExpansionNudgeBanner's state-derived localStorage key exists to manage. With no dismiss, none of it is built and none of it can go wrong. Its non-blockingness is SIZE, not dismissibility. The reason a person may ignore it is that it is one quiet line above the work — not that they are given a control to make it go away. Panel A is what enforces that: any growth in this banner's height is a regression against this decision.

A non-admin sees nothing at all — not a disabled link, not a read-only variant. C2 is drawn IDENTICAL to C1 for exactly that reason. The client gate already exists as useProjectAccess().canManage, and the read behind the count carries the same gate on the SERVER, so the capability is never enforced only in a component.
