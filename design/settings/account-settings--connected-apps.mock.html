Order in the pane: page header → Documentation → Connect the CLI → Your tokens → Connected apps. Below the tokens, because the pane is still the tokens pane and the CLI panel’s tie line already says an approved terminal appears “below” — in the tokens card, which must stay the next thing down. The card carries id="connected-apps", so /settings/account/tokens#connected-apps is a link docs and the consent screen can hand out. No new rail row: the rail is drawn as it ships (lib/settings/accountSettingsNav.ts). The grey dashed slabs are board chrome, not design — those two panels are unchanged.

One row per connection, and a connection is ONE grant (MOTIR-6983 — A connection IS a grant): one person, one workspace, one set of permission keys, one client. So the same app connected to two workspaces is TWO rows (Claude Code, rows 2 and 3), and each revokes alone. Newest first by Connected, the order the token list uses.

App — the client’s registered name in --el-text 500, then the Unverified neutral Pill when the client registered itself (dynamic registration). A client Motir registered for itself draws no pill; there is no “Verified” badge, because the absence is the ordinary case. Under the name, the host its tokens are sent to (the host of the grant’s redirect URI: claude.ai, localhost) in --el-text-secondary — the only fact on the row the app did not choose for itself, so the one that tells two same-named apps apart.

Scopes — summarizeGrant() exactly as the token row: mint Full access, neutral Standard / Read only / Custom, plus the rose Can delete whenever work_item:delete is granted. The chevron discloses every grantable permission in permissionColumnsForTokens()’s split (7 / 7 today, cut after Work items), read-only: a granted row carries a success check, an ungranted row the words Not granted. Nothing on this surface edits a grant — narrowing one is revoke-and-reconnect.
