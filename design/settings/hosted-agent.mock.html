Hosted agent — the model a hosted run uses, by difficulty

The project-settings room that shows which model a hosted run uses for each difficulty — Trivial, Low, Medium, High — lets a project admin override one, and says so when an override stops applying. And the rail row that opens it. Card MOTIR-6991.

Its sibling is the Run hosted picker’s delta, design/runs/run-section--from-difficulty.mock.html, which draws the line that tells the person starting a run where the preselected model came from.

Panel 0 · The access path — a new row in the Automation group, between AI planning and Rules

The room is reached the way every project-settings room is: its rail row (and the matching settings-hosted-agent command-palette deep link the registry lights at the same time). It sits in Automation, directly under AI planning — both rooms choose a model Motir runs on this project’s behalf — and above Rules. The glyph is Cloud, the one the Run hosted button carries, so the row and the door it configures read as one thing.

Availability is a BUILD fact, not a live read. The row keys on whether this deployment runs hosted agents at all (a second SettingsNavAvailability field beside publicProjectsAvailable, defaulting closed). A row that came and went with Motir AI’s health would read as a feature being removed, and a bookmarked URL would 404 mid-outage.

Panel 1 · The room as a project first finds it — every difficulty on its platform default

Four rows, easiest first. Each shows the model a hosted run of that difficulty uses today, and where that comes from. Nothing is overridden, so there is no Reset and Save changes is disabled. The note under the rows answers the question the four rows leave open: what a work item with no difficulty runs on.

Panel 2 · Overriding Low — the shipped Combobox, open, before Save

The per-row select is the shipped Combobox (searchable={false}), offering exactly what Motir AI offers — never a free-text field. Its label is the model id and its secondary text the provider, as in Run hosted’s picker. The row’s own platform default is marked in the menu by the option’s description line, Platform default for Low. The row flips to Override as soon as it is picked; the footer reports Unsaved changes. Picking the platform default again IS a reset — the row returns to Platform default and no override is stored, so an override can never name the model it overrides.

Panel 4 · A withdrawn override — the saved model is no longer offered

Motir AI stopped offering claude-opus-5. The saved choice is not deleted behind anyone’s back, and it is not shown as if it still applied: the select shows what runs actually use (claude-sonnet-5-5, Platform default) and a warning line names the withdrawn model, struck through. Reset to default stays, because a saved override still exists — pressing it clears the dead row. If the model is offered again, the override applies again without anyone re-saving it.

Panel 5 · Read-only — a member who can start runs but lacks ai:configure

Panel 7 · Unavailable — Motir AI cannot be reached

The read failed, which is a different fact from no models offered. The peach Callout says so in words and offers Try again; the rows keep their difficulty labels so the room still explains itself, each select reads Models unavailable (the picker’s own face), disabled, and the source column is empty — the room does not guess a source it could not read. No footer, so nothing can be saved against a list nobody has.
