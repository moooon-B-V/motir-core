10PER PlanStatus — all FIVE, stale included

The enum has five members. The consuming card dispositions four. Every value gets a row, and the two that RENDER are the two the shipped "undecided" predicate names.

value indicator why
generating nothing The frontier is still being appended, so a modify naming this card may not survive to planned. Announcing it announces a claim nobody has finished making. (MOTIR-4197's boundary already excludes it.)
planned renders Closed for review, awaiting a decision. The case the element exists for.
stale renders The value nobody dispositioned. The schema says it outright — "NOT terminal and NOT decided: the plan is live and awaiting action" — and it is reachable only from planned, so such a plan has BY CONSTRUCTION already reached a reviewer. Same copy, same link: whether the plan has drifted is a property of the PLAN, and /plans already carries a Stale pill.
approved nothing Terminal. The proposals ARE the card now; there is no future to announce.
declined nothing Terminal. History, tree untouched.
⚠️ DO NOT REUSE AI_PENDING_PLAN_STATUSES. That shipped constant is ['generating','planned','stale'] and it is correct for its own question — is a planning run in flight for this PROJECT? (saturation, for a prompt). This element asks a different one — is a decision pending about THIS card? — and the two come apart on exactly one member. Declare the element's own set beside the decided pair, with the same totality assertion, so a sixth PlanStatus member turns a test red instead of quietly falling out. That is MOTIR-4129's lesson (merged today, 802f1edfc) applied forward rather than re-learned: classify a predicate by the QUESTION it asks.

Why not tier 3. The late stack is one boundary BELOW THE FOLD; this element sits at the very TOP of <main>, so arriving late would push Description down — and detail-arrival's own rule is that a region either joins the late stack or reserves its own box, never resizes one. It cannot reserve a box either: it renders on well under 1% of item pages, so a reserved banner-sized slot would be a permanent gap on every other card.
What makes tier 2 affordable, measured rather than assumed. MOTIR-3435's surviving half turned the page's twenty-nine serial awaits into a gate plus ONE concurrent group, so a read added to that group costs max(), not sum(). The added cost on a card with no pending plan is therefore one indexed lookup, concurrent — and the index already exists.
12THE READ — named here so the code card MEASURES rather than discovers

MOTIR-4197 AC 2 asks whether the page reuses MOTIR-4106's path or takes its own. Read on origin/main @ 802f1edfc: it takes its own, and the shape already exists.

candidate verdict
aiBoundaryService.readPendingPlans (MOTIR-4106) cannot serve it — it is PROJECT-scoped (does this project have pending plans), returns itemCount and never the proposals, caps at AI_PENDING_PLANS_LIMIT = 10, and lives behind the service-to-service /api/internal/ai/* boundary for a prompt. It cannot answer which plans name THIS card.
planItemRepository.findByWorkItemId(workItemId, workspaceId) this one — its predicate is already exactly { workItemId, workspaceId, op: { in: ['modify','remove'] } }, and it is the drift listener's own first question. Add the plan-status filter (panel 10's set) and the plan's id / title / status to the same query — ONE round trip, never a read per row.
The index exists and is the right one. @@index([workItemId, workspaceId]) — "THE REVERSE INDEX" added by MOTIR-3579, whose own comment says the @@unique([planId, workItemId]) cannot serve a lookup by work item and that the alternative is a sequential scan of every proposal in the workspace. Its leftmost column is this element's predicate. No migration is owed. Report the number in the PR body against a card with no plans; the honest figure is one indexed lookup inside a group that already awaits several.

Why the count is in the headline when modify's is not. A modify's magnitude is not knowable from the row — the patch is a sparse JSON blob, and one field and nine fields read identically — so the shipped headline correctly says only that changes are proposed. An add count IS its magnitude, it is already in the rows the same query returns, and it is the whole difference between a tweak and a story about to gain a subtree. 16The MIXED claim, INSIDE one plan — the case the unique constraint used to make impossible

The right-hand pair is expressible and incoherent, and it is drawn anyway. A plan that archives a card while hanging work beneath it is almost certainly a plan somebody should look at — which is exactly what the element exists to say. Suppressing the children clause to make the sentence tidier would hide the tell. Totality over elegance: the component must be TOTAL over what the query can hand it, and five claims are reachable — modify · remove · add · modify+add · remove+add. A sixth (modify+remove) is excluded by the unique constraint, not by choice.
