The TO-DO LIST on a work item

MOTIR-3808 · MOTIR-3812. A work item carries the ORDERED STEPS of its own work, each one operation, ticked off, carrying its own executor and — where the operation is a command — the command itself with a button that copies it. This asset is the NONE-exists case: design/work-items/ has no checklist surface at all, so the code siblings are blocked_by this card.

It COMPOSES the shipped page. The section is ContentSectionCard's header grammar over the shipped Checkbox, Button and Tooltip, in the left column of app/(authed)/items/[key]/page.tsx. Nothing here is a new primitive, a new colour or a new radius.

Three things it settles that the code card would otherwise have to invent. Where the section sits, measured at 1280×900 rather than asserted (panel 0). Which of the two shipped copy grammars this surface takes — the button's own state, not a toast — and why (panel 2). And the containment rule for a command wider than the column, written down in prose so the section inherits it rather than re-deriving it (panels 13–14).

Two things it deliberately does not draw. The hosted-run control for an agent step, which is MOTIR-3809's; and any status change when the last box is ticked, which docs/decisions/work-item-todo-list.md §3 refuses outright. Panel 6 is what "all done" looks like when it changes nothing.

The left column's shipped order, with the To-do list inserted. Measured, not asserted: at 1280×900 the viewport gives 900px of height, of which the app shell's header takes 56px and the page's own eyebrow + title block takes 132px — so 712px of column is above the fold. Description (≈180px) and Explanation (≈210px) consume 390px of it, which leaves 322px: enough for this section's header plus five rows at 44px. On a card whose work IS the list, that is what the reader came for. Below Relationships the section starts at ≈760px and is below the fold at every measured laptop height; in the late stack it would also be the last region to ARRIVE, which makes the page's most actionable region the slowest.

1bThe row, face one-and-a-half — a step carrying its INSTRUCTIONS, collapsed and expanded.

A to-do is one operation, and performing one operation still takes instructions — go to the dashboard, find the setting, create the token. Those live in notesMd (optional Markdown) beside the one-line text, never as three more tickable rows: navigation is not an operation, and nobody ticks “found the setting”. The tickable unit is the one where done is unambiguous.

Collapsed by default, and the chevron is the tell. It renders only on a row that HAS notes, so a list of ten rows reads as ten lines and the reader expands the one they are on — which is the whole answer to “a body makes the list un-scannable”: it is a rendering question, not a schema one. This is a FIELD, not a second work item — it has no status, no assignee, no dependencies, no sprint and nothing that dispatches it (ADR §1, Instructions).

2The row, face two — a COMMAND step, with the value beside a copy button.

The command is a first-class field, not a substring of the text (ADR §5): the row is copyable because commandText is non-null, never because the text looks command-shaped. 6ALL DONE — a finished LIST, and deliberately not a finished CARD.

Per the ADR §3 the last tick moves nothing: the card's status is untouched, there is no confirmation, and no control appears offering to close it. So the all-done state has to look like a list with nothing left in it rather than like a card that has been completed — a tinted banner saying Done would read as a status, which is exactly the claim this surface may not make. A quiet line under the rows, and the header's own 3 of 3, are the whole treatment.

7READ-ONLY — an actor without work_item:edit.

They keep the information and lose the controls: the rows, the marks and the count all render, and there is no add row, no drag handle, no edit, no delete. The checkbox is genuinely inert, not disabled-looking — it is rendered as a static role="checkbox" with aria-disabled, so a screen reader announces the state and offers no action, and there is no control to click that silently does nothing.

8ADDING — the composer is the last row, not a modal.

A step is one line, so asking for a dialog to type one would cost more than the step. The input appends at the END (the fractional index's keyForAppend), Enter commits and keeps focus in the field for the next step, Escape abandons. The command and the executor are set from the row's own menu after it exists — a composer that asked for three fields up front would make the common case (a plain step) the slowest one.

9EDITING a row in place — three kinds of text, three different controls.

The row becomes its own editor, and it carries THREE controls because it holds three different KINDS of text. text is plain and one line → an Input. notesMd is Markdown → the shipped MarkdownEditor at size="compact", the same composer the comments section on this page already renders, whose button set is bold · italic · strike · inline code · link · bulleted · numbered (components/ui/MarkdownEditor.tsx). commandText is one line of mono → an Input again, never a rich-text surface. A field the product STORES as Markdown and EDITS as plain text is a field whose numbered list and link a user can only produce by typing the syntax blind — which is the mismatch this panel exists to close. The executor is a two-value control beneath them. The patch is sparse — clearing the command field to empty sets it to null and the row stops being copyable, while leaving it alone leaves it alone (MOTIR-3814's action contract).

10DRAGGING to reorder — and its keyboard equivalent.

The dragged row lifts as a dashed ghost and a 2px accent rule marks the drop slot. The write is one row: the fractional index mints a key between the two neighbours at the destination, so nothing below the moved row is rewritten. The handle is a real button — Space picks the row up, Arrow-Up/Down moves it a slot at a time with the position announced, Space drops it, Escape restores it. A drag-only reorder would make the one editable thing on this surface mouse-only.

11DELETE — an inline confirm on the row, and where focus lands afterwards.

One step is a cheap thing to lose and a cheap thing to retype, so the confirm is an inline swap on the row rather than a modal — the Modal primitive is reserved for the irreversible. After the delete, focus moves to the NEXT row's checkbox, or to the add-step field when the deleted row was the last one; it never falls to the document body, which is how a keyboard user loses their place in a list.

12AT SCALE — twenty steps. The section GROWS; it does not cap and it does not scroll.

A to-do list is bounded by the granularity bar in the other direction: a card needing forty steps is a card that should have been two cards, and the right place to say so is the plan, not a +14 more control that hides the work. So the section grows with its content, as Children and Relationships do, and the header's count is what makes a long list legible without scrolling it. This is the one region on the page where an inner scroll would be actively wrong: the reader is working THROUGH the list, and a scroll container inside a scrolling page is where a step gets missed.

13OVERFLOW at 1280 — the long command scrolls INSIDE ITS OWN box.

The containment rule, written down here so the section card inherits it rather than re-deriving it: the mono value is its own overflow-x-auto container; the row's body cell carries min-w-0; the copy button carries shrink-0. All three are load-bearing. Without min-w-0 a grid/flex child's minimum size is its CONTENT, so the row widens and the PAGE scrolls sideways instead of the command. And a Button in a flex row defeats min-w-0 on its own account unless it is explicitly told not to shrink. The box is tabindex="0" so a keyboard user can scroll it — a box that scrolls its own content is a box that must be focusable.
