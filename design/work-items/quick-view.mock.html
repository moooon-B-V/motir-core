Let a returning user sign in with their email address and password. Validate the credentials against the stored argon2id hash, establish a session, and route the user to the workspace they last visited.

The affordance is the ROW, and the chevron is its marker. The detail rail hangs its chevron in FieldCard chrome; the peek's rail has no card, so the chevron sits inline on the caption line, right-aligned — it costs no vertical space in a 300px column already carrying fifteen rows. It is always rendered at --el-text-faint and only strengthens to --el-text-secondary on hover/focus: reveal-on-hover alone is unreachable on touch and invisible to a keyboard user. The whole row is the hit target; the chevron is a real <button> with an aria-label="Edit <field>", so the rail stays a <dl> and each control is individually reachable by tab.

Order, density and content are unchanged from 8.8.4 — this panel is deliberately diffable against panel 2. Reporter and the Created / Updated line carry no chevron, because the detail rail does not edit them either (the story's rule: the peek edits what the detail rail edits). The Show more fields (2) disclosure is relabelled “2 more fields”: in 8.8.4 it hid clutter, and it is now the only way to REACH an empty custom field, so a label promising only to “show” it would be wrong.

Why the menu is in flow and not floating. @motir/design-system's Combobox and MultiSelectPicker portal their listbox to <body> with position: fixed — except when they detect an enclosing role="dialog", where they render it INLINE instead. Both branches already ship. The peek IS that dialog (Modal.tsx wraps @radix-ui/react-dialog), so the inline branch is the one that runs here and the design must draw it: the menu is a block below the trigger, inside the rail's own overflow-y: auto column.

The consequence, and it is the one thing this panel decides: a menu near the bottom of the rail does not float over the modal edge — it EXTENDS the rail's scroll height, so the rail scrolls to it. That is correct and needs no new mechanism, but it does mean the code card must scroll the opened control into view rather than assume it is visible. The control is full-bleed to the 300px column so it never reflows the two-column body.

Pending shows no spinner, and that is deliberate. The picked value is ALREADY on screen — the rail commits optimistically and the action response is only the confirmation (the rule app/(authed)/items/_components/IssueInlineEdit.tsx was rewritten to enforce after bug-inline-status-revert-on-second-edit). So pending dims the value and runs a hairline bar under it; it never disables the row, blanks the value, or shows a spinner where the answer already is. Confirmed is a check beside the caption that fades; there is no toast for a success nobody needed to be told about.

Refused is a FIELD message, not a toast. The peek owns the viewport, and a toast about one field would appear far from it. The value reverts to the served one and the typed reason sits under the row. The danger hue is on the GLYPH only — --el-danger-text is #ffffff (it is ink for a danger FILL, not a label on a surface), and --el-danger as text measures 4.25:1 on the dark page, under AA at this size. A glyph needs 3:1, so the hue carries the meaning and the words stay on --el-text, readable in both themes.

Stale is not a field error — it means the whole payload is behind, so the peek re-reads and the notice sits at the TOP of the rail naming the reload, above rows that may all have moved.

A collection row has no single commit moment, so it does not swap its value for one control. It stays a chip stack and gains two affordances: each chip carries a remove ×, and a dashed + Add chip opens the MultiSelectPicker. The row stays in edit mode across several adds and removes — which is why the chrome's optimistic ledger has to survive repeated writes to the same row rather than one write per open.

Read-only is a DRAWN state, not the absence of one. An actor without work_item:edit gets exactly the 8.8.4 rail — no chevrons, no + Add, no remove ×, no disclosure change. Not disabled controls: absent ones. A disabled chevron advertises a capability the viewer does not have and invites a click that can only fail.

12 · What the row behind the modal does

While the peek is open — the row behind is stale, and stays stale

PROD-23 Email + password sign-in to-do M

On close — one re-read, and the row is current

PROD-23 Email + password sign-in in-progress P

The decision: the host surface re-reads ONCE, on CLOSE, and only if at least one edit was confirmed. Not per edit, and not never.

Not per edit, because that is the shape that already caused a bug here: refreshing the route on every successful inline edit shipped a full RSC snapshot per keystroke-sized change, two quick edits raced, and a stale snapshot landing last repainted an unrelated row with its old value (bug-inline-status-revert-on-second-edit; the reasoning is preserved in IssueInlineEdit.tsx and in the header of app/(authed)/items/[key]/edit/actions.ts). Not never, because a list that contradicts the change you just made is worse than one that lags — and the user is looking straight at both.

Close is the only moment that is both safe and sufficient: the modal is going away, so no optimistic cell can be repainted by the re-read, and the user's next glance is at the list. Both peek drivers must do it — IssueQuickViewController.tsx (URL-driven, over /items, /ready, /boards) and components/planning/WorkItemQuickView.tsx (local state, on the planning canvas). They are separate files with the same job; a signal added to one and not the other is how the canvas peek silently becomes a different product.

The canvas is a client island, so router.refresh() does not reach it (the page-state-after-mutation contract, case 3) — its driver needs an explicit refetch of the node it peeked, not a route refresh.
