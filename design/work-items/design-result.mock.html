0 · Placement, and the access path

The section sits in the item-detail LEFT column, after Development and before Children — the same slot family as the acceptance panel, which is likewise detail-page only. It renders on any leaf that has a current design result, and on a type: design subtask that has none it renders the empty state (panel 3) rather than disappearing, because "no design published" is a fact worth stating on the card whose job was to produce one.

2 · The mock frame, MEASURED

The frame is 32rem (512px) tall and scrolls inside itself, in both axes. A published mock is a tall multi-panel document — acceptance-panel.mock.html is 48 KB of stacked panels — so an unbounded frame would swallow a page that already has eight sections. 32rem shows roughly one panel of a real mock at a glance. Measured below against a 900px viewport: header + note + frame + screenshot still leave the sections below reachable by ordinary page scroll.

Horizontal. A mock wider than the content column scrolls inside the frame (the inner block above is 46rem against a narrower column). The page body never gains a horizontal scrollbar.

The escape. Open in new tab is the full-width read, and it is the only affordance the frame carries. Nothing here requires script INSIDE the iframe: the sandbox grants neither allow-scripts nor allow-same-origin, and the shipped assets tolerate that because they are self-contained inline CSS with no <script>.

Consequence, stated: a mock that needs JavaScript to render appears inert. That is the intended trade — a design mockup is a static artifact, and the .png plus the new tab remain.

3 · Nothing published yet

The most-seen state for a long while: every design subtask that shipped before this feature has no published result. It must read as "this design predates the feature", never as an error, and it says where a result comes from so nobody goes looking for an upload button.

4 · Loading, and a frame that fails

The note and the screenshot render server-side, so only the FRAME has a loading state — the signed content URL resolves on the client. A frame that fails (an expired signature, a store outage) offers a retry and keeps the note and the screenshot readable; it is never a blank rectangle, and it never takes the rest of the panel down with it.

5 · Superseded — and what happens to the old one

Every push to the design PR republishes, so a card accumulates history. The panel shows the CURRENT result and says when it landed. Prior results are NOT reachable from this panel in this iteration — deliberately, and said out loud here so the next reader does not take the absence for a bug. The rows are retained in the database (superseded, not deleted), so a history affordance is a later addition that needs no migration; what it must not become is a silent gap.
