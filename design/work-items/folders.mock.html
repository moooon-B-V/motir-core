The row. A folder row is the SAME treegrid row as a work item's: 40px, the 22px indent, the chevron. Its whole-row target is a <button> that expands and collapses — never a link, and never the quick view, because a folder has none (MOTIR-5315). Folders sit ABOVE the level's work items in their own order, and a column sort reorders only the work items (MOTIR-5314). The seven work-item cells stay empty: a dash reads as "unset", and a folder has no priority to be unset. The menu is the one place folders differ from work items on purpose — work-item rows lost their menu in MOTIR-4258 because their quick view carries every door; a folder has no quick view, so its row is the only place its actions can live. The actions button is always rendered, never hover-only, for the same touch and keyboard reason the rail's chevron is. "Move up" is disabled on the first folder of a level and "Move down" on the last. "Delete…" takes the ellipsis because it opens a confirmation (panel 5).

Inline, not a dialog. A folder's only field is its name, so the name is edited where it is read. The input takes the row's glyph and indent and spans the row; Enter saves, Esc and blur-with-no-change cancel. Names are trimmed, 1–120 characters, and unique among siblings ignoring case — "parked" collides with "Parked" (MOTIR-5313). The refusal keeps the input open with the typed value, marks it aria-invalid and says why under it; a race the unique index catches arrives as the same typed error and renders the same way. An empty name is refused with "Enter a name." A new folder is created where the service puts it: after the level's last folder and before its work items, so the input row appears exactly where the saved row will stay.

4 · Move to… — the folder picker for "2025": Project root plus the project's folders; the folder itself and everything inside it disabled with the reason. Right: a refused move

Move “2025” to…
A folder can’t move into one of its own folders.

One picker, two modes. This is the component MOTIR-5315 builds once and MOTIR-5316 reuses: a search field over the project's folder tree, where picking an option commits — there is no second "Move" button, as there is none on any rail picker. In move a folder mode it offers Project root, marks the current parent "Current location" (picking it writes nothing), and disables the folder and every folder under it with the reason in words, not only by greying. A cycle the picker could not know about — the tree changed under it — comes back as FolderCycleError and is shown at the top of the open picker with the list re-read; a CrossProjectFolderError ("That folder belongs to another project.") renders in the same place. The picker is a popover anchored to the row in the tree; inside the quick view's dialog it renders in flow (panel 6). Reorder is "Move up" / "Move down" in the menu, not the picker: the tree has no drag affordance anywhere today, and this adds none.

5 · Delete confirmation — it names what moves up and where, and says no work item is deleted. Right: an empty folder, with lighter copy

Delete folder “Parked”?

2 folders and 3 work items will move to Project root. No work items are deleted.

Delete folder “Spikes”?

“Spikes” is empty. Deleting it removes only the folder.

The shipped delete dialog, told the opposite story. The work-item delete (delete-confirm.mock.html) warns that descendants go with it. A folder delete moves its child folders and filed work items to the deleted folder's own parent, in one transaction, and removes nothing else (MOTIR-5313) — so the consequence line uses the mint safe-outcome callout, not a warning list, and names the counts and the destination ("Project root", or the parent's name). Counts are of DIRECT contents: a filed epic counts once, and its stories travel with it. The danger button still says "Delete folder" — the folder itself is gone. Default focus is Cancel; Esc and the close button cancel. After confirming, the folder's row leaves the tree and its parent level is re-read so the moved contents appear in place.

The door every other field already uses. Folder is one more editable rail row (QuickViewRailEdit), directly below Parent: the same caption-line chevron, the same in-flow menu inside the dialog, the same pending bar, confirmed check and refused revert (quick-view.mock.html 7–9). Its value is the folder PATH, "Later ▸ 2025", or "No folder". The menu is the panel-4 picker in file a work item mode: No folder plus every folder, the current one checked, nothing disabled (MOTIR-5316). Because an item sits in a folder OR under a work-item parent, never both, opening the field on an item that has a parent says so BEFORE the save — "Filing it removes it from PROD-12 Q3 launch." — and after it Parent reads None. Picking the current folder writes nothing. A refusal reverts the value and puts the reason on the row. Behind the dialog the tree updates in place: the row leaves its old level and appears under its folder when that level is loaded, children still beneath it (the lavender landing tint here is board annotation only). The field keeps its optimistic value on success and is not re-fetched.

Empty. An expanded folder with nothing in it shows one quiet row at the children's indent, so an empty folder never looks like a load that failed. Paging. A folder's level pages exactly as a work item's children do — the shipped "Load more children · Showing N of M" row at the end of the loaded rows (MOTIR-5314). Read-only. Without work_item:edit the affordances are ABSENT, not disabled — no "New folder", no actions button, no Folder chevron — the rail's existing read-only rule (quick-view.mock.html panel 10); the service's own refusal is the backstop. Folders are still shown and still expand. Dark. Every colour above is an --el-* token, so the stage re-skins with nothing folder-specific to flip.
