The planner SPEAKS in the plan-change thread

MOTIR-2225 · an amendment to design/ai-chat/, sibling to plan-change-conversation.mock.html. MOTIR-2222 gives the planner a voice — a findings report on every turn, and one clarifying question when the request is genuinely not determinate. This is the room it speaks in. MOTIR-2226 builds it.

Two things are genuinely new: the planner's utterance is persisted — it belongs to the thread's history rather than being local chrome — and the thread can be blocked on the user. Everything else is composition. The load-bearing decision is the one in panel B: most turns are reports, so a question that reads like a report is a dead thread.

A

The findings report — the planner says what it looked at, before it proposes

Every planning turn now opens with a report: what was searched, what came back, and what that means for the request (MOTIR-2222, Gate 1). It is an ordinary assistant bubble — the same fill, ink, avatar and width as the opener and the proposal summary the rail already shows. That sameness is the design: on most turns the planner is narrating, not asking, and narration that looks like an ask trains the user to skim asks.

B

The question — and the whole rail waiting on it

When the request admits two materially different outcomes the grounding cannot rank, the planner asks one question and stops. This is the state that must be unmistakable, because it is rare: a question that reads like narration is a thread that dies silently, with the user waiting on a planner that is waiting on the user.

What tells them apart

A report changes only the transcript. A question changes the composer.

report question
bubble fill --el-chat-bubble-ai --el-warning-surface
bubble ink --el-text --el-warning-text
label slot none asking + ? glyph
answer bar — pinned above the composer
placeholder Reply, or refine further… Answer Motir AI…
Send button icon only icon + Answer
canvas proposals land untouched

Three cues, none of them colour alone: a word (asking / Waiting for your answer / Answer), a glyph (lucide message-circle-question-mark), and a position — the bar sits against the input, which is pinned, so the state is legible with the thread scrolled anywhere.

No dashed or dotted border carries this state. Pending is a token-driven tint plus a label; a hardcoded dashed edge would fight the data-style axis and collide with the canvas's proposed-node language.

Why the bar and not a header pill: at the rail's real 22rem the header already carries the status dot, the Motir AI label and the mode chip — a fourth element would truncate. The bar has the full width, sits in the pinned region, and is adjacent to the control whose behaviour actually changed.
C

The answer, the resumption — and what you come back to

The answer is an ordinary user turn, labelled answer in the slot user turns already number themselves in. Resumption is announced with the shipped submission-marker vocabulary (centred, faint, --el-text-faint) — no new element. The pending state is derived from the persisted thread, not held in client state, so navigating away and returning restores exactly what you left.

E — the disposition is DECIDED here, not left to the code card: a question is SUPERSEDED, never dropped and never blocking. The moment the user sends anything else, the pending state clears — the bar goes, Send is an icon again, the placeholder returns — and the planner proceeds on its own best reading of the original request.
