The RESIZABLE planning split — the default third, the divider, the bounds, and the reset when a plan is proposed

MOTIR-6249 · a delta on design/ai-chat/, amending planning-workspace.mock.html (MOTIR-1193), which drew this frame with a constant 22rem conversation column. The requester's words, on MOTIR-6236's design gate: "The right conversation window is too narrow, so the textarea is too narrow too. We give one-third of the width to the conversation window initially, and the user can drag the width freely to change the width of both windows. When the plan is proposed, we reset the canvas width to 2/3 of the width."

Six decisions this asset settles, so the code card builds them rather than choosing them: the default as a number and what it is a fraction OF (sheet 1); each pane's minimum and maximum, with the reason each bound is where it is (sheets 5 and 6); the divider's visible width and its hit area (sheet 2); whether the reset is animated and over what duration (sheet 8); whether a dragged width persists (sheet 9); and the narrow-viewport breakpoint and behaviour (sheet 9).

Nothing inside either pane changes. This card draws the FRAME and the SEAM. The rail's own contents are MOTIR-4066's render, reproduced untouched; the canvas's contents are MOTIR-6155's and MOTIR-6158's; the composer's own panels are MOTIR-6236's, re-scoped by the widths settled here.

The percentage is of the split container, never of the viewport, because this split ships in two containers: the full-screen workspace, where the container IS the viewport, and the plan page, where the app shell has already taken 306px. A viewport fraction would hand the plan page a conversation wider than a third of what its reader can actually see.

the anatomy, at 8× — the visible line and the hit area

1px visible — --el-border, the rail's own edge value.

11px hit area — the line plus 5px either side, absolutely positioned over the seam so it costs the grid nothing and neither pane moves when it lights up.

11px is the narrowest strip a pointer acquires without aiming. It is deliberately not the answer to the 24px target-size guideline — a full-height splitter has no 24px width that is not a visible slab, so the answer to target size here is the keyboard control in sheet 7, which is exact at any size.

Shape and colour go through the element layer only. The line is --el-border → --el-border-strong → --el-accent across rest → hover → drag, and no state paints a raw hue or a Tier-0 --color-*.

4

Dragging — live re-layout, the pointer captured, and the canvas transform left alone

The line becomes --el-accent at 3px. Four decisions, and the first is the one the requirement actually turns on: (a) the panes re-lay-out LIVE, on every pointermove, coalesced into one requestAnimationFrame — not on release. You are choosing a width for text you are reading, so you have to watch the text reflow while you choose; a release-only resize makes it a guess you repeat. (b) The pointer is CAPTURED (setPointerCapture), so the drag survives leaving the 11px strip and the cursor stays col-resize across the whole window. (c) Nothing is dimmed or frozen — both panes keep rendering; only text SELECTION is suppressed (user-select: none on the frame), because a drag across a transcript otherwise selects it. (d) The canvas keeps its own pan and zoom untouched: no re-fit during the drag and none on release. A re-fit would make the level jump under the pointer, and a wider canvas revealing more of the world is the correct answer to a wider canvas.

the three things that have to stay usable at the floor
  • The composer field. The shipped <input> is exactly 44px (--height-input) and takes the row's remaining width; at 352px it is the width it is today, which is the width MOTIR-6236 is drawing against.
  • The target tray. The @ trigger is position: absolute; left: 1.5 inside the control row, so it costs the field no width at all — it is unaffected by the floor.
  • Send. A sibling of the field in one flex row, not a child, so it keeps its own intrinsic width and the field yields first. It is legible at the floor because the floor IS today.

Nothing here is new work. That is the argument for this floor: at 352px every element in the rail is at a width somebody has already drawn, so the minimum state needs no design of its own.

352px is also the default below 1056px (sheet 1's table), so on a 768–1056px split the "minimum" and the "default" are the same state — the frame opens exactly as it ships and the divider can only travel one way.

At the maximum conversation — half the container, because a rail stops being a rail past half

The ceiling is 50% of the split container — 720px at 1440. Not a canvas pixel floor, and the reason is a measurement that cuts the other way: lib/planning/canvasGeometry.ts puts a three-column level at 800px wide at the 0.80 legibility floor, which with arrivalView's 48px padding wants an 896px canvas — and the shipped surface is already below that at ordinary sizes (planView.ts measures a width term of 0.526 at 1280×800). So a canvas pixel floor would be a floor the product does not honour today. What does not recover is the MODEL. This area is built on "the canvas IS the roadmap; the chat is a right rail" (design-notes.md, the first section). The canvas's legibility is recoverable at any width — it pans and zooms — and the model is not: past half, the rail is the surface and the canvas is the companion, which is the opposite of what a proposed plan is read on. Half is the last width at which the sentence is still true.

three things the requirement leaves open, settled here
  • It fires ONCE, on the transition into "a plan is proposed" — not on every render while one is on screen, or a person who drags wider to read a long card is fought by the layout every time the rail re-renders.
  • It does NOT clear the stored width (sheet 9's persistence). The reset is a one-shot return for reading THIS plan; the width the person chose is still theirs and comes back next time they open the surface. A reset that also forgot the preference would punish dragging.
  • It is a no-op when the conversation is already at or below the default. There is nothing to give back, and animating a frame that is already right is a flicker with no content.
The canvas is not re-fitted by the reset either — same rule as the drag (sheet 4). The column animates; the canvas's pan and zoom are the person's and survive it. What a proposed plan does to the canvas's own view is MOTIR-6155's and MOTIR-6158's, and this card does not touch it.

why 768px and not a new number

At 768px the two bounds have already closed on each other: the floor is 352px and half the container is 384px, so the whole travel is 32px and the canvas is between 384px and 416px whatever anyone drags. A divider whose entire range is 32px is a control that cannot pay for its own chrome. Below 768px the stack is the only layout that leaves either pane usable, which is what the shipped breakpoint already decided — so this card inherits it rather than inventing a second one.

persistence — settled, with the mould named

A dragged width PERSISTS, in localStorage, under one global key (motir.planning.railWidth), as an integer of CSS pixels. Not per project, and not per visit. The mould is the one this repo already has four of — lib/hooks/useSidebarCollapsed.ts, and useCommentsSort, useAttachmentsView, useCollapsedLanes beside it: a module-level cached store, the initial value read lazily once on the first client render, the server render taking the stable default, and a write failure accepted rather than surfaced.

Why global rather than per project: the number is about this person's screen and how they read, not about a project — and every member of that existing family is global, so a per-project key would ask someone to re-choose a width on every project they open and buy nothing. Why persisted rather than per visit: a width you have to re-drag every time is a width you stop dragging, and the reset in sheet 8 already covers the one case where a remembered width is in the way. The read is CLAMPED into the current container's bounds — a 900px conversation stored on a 2560px monitor opens at half of a 1440px laptop, not at 900px.

The stored width is a preference, not state to migrate. It is localStorage, per browser, and losing it costs one drag — which is exactly why it does not belong on the user record or in a query parameter. The code card decides where the hook lives; it does not get to re-decide this.
