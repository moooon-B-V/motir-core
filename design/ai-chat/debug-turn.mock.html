The debug turn in the Motir AI rail

MOTIR-7045 · story MOTIR-7042. A turn the server reads as debug reads the code, names the likely cause, checks whether a card already covers the bug, and then writes to exactly one card. It moves no status and promotes nothing (A1.4). The rail draws it with the parts it already has: the user bubble, the act rail, the assistant bubble, the marker line and the shipped paywall. It adds one new element, the outcome line that names and links the card the turn wrote to.

Both entrances end here. The report widget's accept (design/triage/report-widget--debug-offer.mock.html) sends the turn anchored on the triage bug it just filed. The orb row (ai-callout-menu--debug-row.mock.html) pre-fills the composer, and the person sends the turn themselves, with no anchor. The panels below use the widget path, and each finished panel shows the orb path's variant of the outcome line.

The prose is Motir AI's; the outcome line is Motir's. The bubble body is the model's diagnosis, rendered through MarkdownView like any assistant turn. The outcome line is new. It sits in the answeredFrom foot slot (hairline --el-border-soft, 12px) and is built from the job's result, not from the model's words. So it always names the one card that was written, even when the prose does not mention it.

The link is the shipped work-item chip. WorkItemRefChip is the same chip an answer cites with (bug hue --el-type-bug, key --el-link, on --el-surface-soft). Clicking it opens the shipped peek, not a navigation, so the person can read what was written and keep talking. A triage bug resolves by key (A1.2), so the chip and the peek work for it.

“It stays in Triage” is load-bearing. The write does not promote the bug and does not change its status (A1.4). The line says so, so the person is not left looking for the bug on the board.

Correction (§3, A1.5). The latest assistant turn carries the shipped correction marker. Under a debug result it reads “Answer this instead”. It re-runs the same user turn as ask, and the diagnosis already written stays on PROD-412. After a re-run, the shipped “Re-read as a question” marker sits above the new answer.

The existing card is named twice, on purpose. The prose cites it where it explains the match. The outcome line names it as the card that was written to. The first is an argument and the second is a record. Only the second is guaranteed to appear.

The person's own report is accounted for. On the widget path the turn was anchored on PROD-412, and A1.4 leaves it as it is when another card already covers the defect. The line ends “PROD-412 is left as it is”. It is plain text, not a second chip, because the turn did not touch it. Marking it a duplicate stays the Triage inbox's act.

An enrichment adds and never replaces. What a person wrote on PROD-318 stays as it is (A1.4). The field-level shape of what is added belongs to MOTIR-7049, not to this drawing. The existing card keeps its status (the in-progress dot here), because a debug turn never moves one.
