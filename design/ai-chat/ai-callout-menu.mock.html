The “M” universal AI callout — the orb becomes a trigger

The shipped floating “M” orb (PlanWithAIFab, MOTIR-1299) navigates straight to the planning workspace today. This design turns it into the trigger for a small anchored menu — “the home of all AI” — whose first action is Plan with AI, with Ask about this project (MOTIR-1343) and Help with a task (MOTIR-1344) mounting into the same menu as their stories land.

⭐ EVERY ROW OPENS THE SAME SURFACE. The menu only says what the callout can DO. Motir has exactly one AI conversation surface — the PlanningWorkspace at /planning (MOTIR-1729) — and all three rows navigate to that one surface, with the same context-derived href, via the shipped planningWorkspaceHref(). The callout is not a mode picker and not a router: it is a capability list — an answer to “what can I ask this thing?” — and the row you pick does not narrow what the conversation can be about.

Why (Yue, 2026-08-01): the conversation is free-form, and the user can switch topic mid-conversation — plan the sprint, then ask what blocks a card, then get help drafting its description, all in one thread. A mode chosen at the door would be wrong within one turn, and enforcing it would fragment the one surface the product deliberately has. So the door does not choose; it only advertises.

It deepens planning-workspace.mock.html sheet 4 (“B — Floating ‘M’: the universal AI callout”); that sketch’s visual language is settled and reproduced here. The orb’s own fill, glow and pulse are reused exactly as shipped — this asset never re-specifies them — and the planning workspace itself belongs to 7.20.1 / MOTIR-1193.

  • An action whose story has not landed is ABSENT — never a dimmed, disabled, or “Coming soon” row. A dead row is a promise the product cannot keep, it costs a tab stop and a screen-reader announcement, and it makes the interim state feel broken rather than young.
  • Equally forbidden: a row that opens a bespoke per-feature chat panel. Every row is a door to the ONE workspace.

The four states

rest no fill hover --el-surface focus-visible --el-surface + inset ring active / pressed --el-muted
  • hover === focus-visible fill, exactly as the shipped UserMenu row does (hover:bg-(--el-surface) focus-visible:bg-(--el-surface)) — the keyboard user and the mouse user see the same highlight.
  • focus-visible adds a ring the shipped row lacks. On a 240 px menu of one-line rows a fill alone is readable; on a three-row callout with descriptions it is not distinct enough, so the row also draws the 2 px --focus-ring-color ring, inset so it never clips at the panel edge.
  • Use --radius-control, not --radius-sm. The shipped UserMenu rows render rounded-(--radius-sm) with raw px-2 py-2 — Tier-0 shape that a data-style swap cannot reshape. The new rows take the element-semantic tokens; the rendered values are near-identical today, so nothing looks different and the style axis is honoured.

Open · close · keyboard — the shipped UserMenu popover idiom, unchanged

no role="menu" · no roving arrow keys

The flow

  1. Open — click, Enter or Space on the orb. Radix opens Popover.Content in a portal, moves focus into the panel, and flips the trigger’s aria-expanded.
  2. Move — Tab / Shift+Tab walk the rows in DOM order (and the composer last, once it exists). Natural tab order, Radix-managed containment — not a roving menuitem model.
  3. Activate — Enter follows the row’s href into /planning; the panel closes on navigation. Every row carries the SAME href, so which one is activated changes nothing about where the user lands. ⌘/middle-click opens it in a new tab, because the row is a real link.
  4. Dismiss — Esc, or a click anywhere outside.
  5. Focus returns to the orb on every close path (Radix’s onCloseAutoFocus default) — the keyboard user is put back where they started, never at the top of the document.

Why no role="menu". The shipped shell menu (UserMenu) is a Popover whose content renders as role="dialog" holding plain links — verified in the running app. A second, contradictory interaction model for the callout would make two shell menus behave differently under the same-looking chrome. If a future card genuinely wants arrow-key roving it must say so explicitly and specify the FULL menu / menuitem semantics (aria-activedescendant or roving tabindex, typeahead, Home/End) — it is not something to half-build.
