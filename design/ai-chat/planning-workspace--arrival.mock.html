The planning surface's canvas opens INSIDE the node being planned

A delta on design/ai-chat/planning-workspace.mock.html (sheet 6) and its notes section Opening & exiting. Only the panels that change are drawn. The frame, the scrim, the canvas·rail split, the exit chrome and the footer slot are sheet 6's and are inherited unchanged.

What is overturned: the rule that the workspace opens on the anchor's own level among its siblings — stated in code at components/planning/PlanningWorkspaceOverlay.tsx, the ANCHOR READ block, as “ANCESTORS ONLY (MOTIR-2070) … Opening on the anchor's CHILDREN would hide the item the conversation is about.” This design answers that objection rather than ignoring it: panel 2 is the answer.

The TARGET CRUMB — the answer to MOTIR-2070's objection

MOTIR-2070 was right that standing inside the item removes the thing the ring was for. The answer is not to keep the ring: it is to move the mark to where the target now is — the last crumb. It reuses the FOLDER crumb's shipped seam (a leading 14px lucide glyph plus a visually-hidden prefix, the folder / srPrefix props on the canvas's own Crumb), so the breadcrumb grows no new shape — only a second crumb KIND. Glyph: lucide target, the same mark the node pill already carries, in --el-accent-on-surface.

Element Token / primitive Why
Target glyph --el-accent-on-surface, lucide target, 14px The accent AS ink on a surface. The same glyph the shipped PlanningTargetFrame pill uses, so “target” means one thing on this surface whether the target is a node or the level.

A subtask is the single structural leaf in the kind matrix (lib/issues/parentRules.ts: subtask → [], everything else may parent). A leaf has no inside, so the canvas opens on its own level and the target keeps the RING; the breadcrumb ends at the parent.

At the root the canvas draws no breadcrumb at all — measured on the real component, not assumed — so there is nothing to name a target in until the move happens. The move fires once, when a target first becomes known: the person adds one to the composer's target set, or the plan's proposals first show where the plan lands.

The person NAVIGATED FIRST — the canvas does not move

A deliberate navigation outranks the follow-move, always. But saying nothing strands them: the plan is landing somewhere they are not looking. 8

The ACCESS PATH — five entrances, one arrival rule

Every door opens the overlay on the page it sits on; none navigates (sheet 6). What this design changes is what the canvas does once it is open — and it is one rule, reached the same way from all five.

Entrance What the address carries Where the canvas arrives
Plan with AI on a work item planFrom=work-item + planItem=<key> Inside that item (panel 1) — or on its own level, ringed, if it is a subtask (panel 3).
A Plans row planSession=<id> + planVia=plans, with planItem= when that session has a target The same arrival as Plan with AI for that session's target.
A To approve row planSession=<id> + planVia=approvals, with planItem= when the plan has a target The same arrival again — which is the point: a plan you are being asked to decide opens where its cards are.
⌘K / the global launcher planFrom=project, no item The root — then the follow-move when a target settles (panel 4).
The project launcher / roadmap empty state planFrom=project or roadmap, no item The root, then the same follow-move.

No new address parameter. The To-approve row already writes planItem= when its plan has a target (MOTIR-6033's published design, §20.2), so all three targeted entrances hand the arrival rule the same key. That is what makes “one arrival rule” true rather than aspirational.

The same card, twice, side by side. Left: the committed card, which knows it is done — --el-tint-sky fill and a struck title. Right: a modify proposal over that same card, which cannot say so: PlanItemNode has no done treatment, so it falls back to the default shell and a status pill resolved from the proposal envelope. The 2px padding difference is visible here too, between two cards one gap apart. The change ring and badge are correct and stay — they are the op.

THE RULE. There is ONE card shell — footprint, radius, border weight, padding, shadow, and the kind bar · identifier · title · status row — and it has ONE implementation. A proposal's op treatment, the target ring and the plan-change diff frame are LAYERS OVER that shell, never second drawings of it. Two of the three layers already work this way and say so in their own source: PlanningTargetFrame — "It WRAPS the shipped node — the same compose-don't-redraw seam PlanChangeDiffFrame uses". The op layer is the one that does not.

Shell property Committed card Proposal card Verdict
footprint 280 × 124, both — NODE_W / NODE_H one
radius · border weight · shadow rounded-(--radius-card) border shadow-(--shadow-card), both one
padding p-3.5 — 14px p-3 — 12px DRIFT Two cards on the SAME level are inset differently. No op treatment needs it. One value: p-3.5, the committed card's, which is what the roadmap ships and what most cards on any canvas are.
kind tint map KIND_TINT is declared twice, identically — once per component DRIFT One exported constant. The status vocabulary was already collapsed this way, for this reason.
border style · colour · fill --el-border / --el-surface dashed --el-accent / --el-tint-lavender KEEP This IS the op, and it is the layer's whole job.
state vocabulary ready · done · here · not-in-sprint · cross-blocked none of them — no such props GAP After the plan is proposed, a committed sibling can say Ready or Done and a proposal beside it never can. A modify of a done card draws as if the card had no state.

What follows for the three surfaces, and it is short: surfaces 1 and 2 already draw the identical component, so "the same in the roadmap and on the planning surface" is true today — and that is the real constraint this design puts on MOTIR-6160: changing where the canvas STANDS must not change what a card LOOKS like. Surface 3 differs by one padding value, one duplicated constant and one missing state vocabulary. Fixing those is not this story's work — it touches no arrival and no follow-move — so it is filed as its own card rather than absorbed here.

Not drawn here, on purpose. What the canvas DRAWS once it is on the level — a proposed plan's List | Canvas views, and cards arriving with their edges while the plan is written — belongs to the review story and the live-drawing story. This delta decides only WHICH LEVEL the canvas stands on, what the breadcrumb says about it, and (panel 9) that moving the canvas may not change the card.
