THE DECISION — edge to edge, and sheet 6's own “slight inset + drop shadow” prose is superseded. Three reasons, in the order they decided it. (1) An inset is a REGRESSION against what ships today: the route host is already h-dvh w-full with no shell chrome, so the edge-to-edge overlay gives the canvas the identical box and an inset takes 48px in each axis away from it. (2) design/roadmap/'s fit-floor work (MOTIR-3837) fought for +120px of canvas height at 1440×900 on the surface with the most canvas need; handing 48 of that back to a margin is the same argument running backwards. (3) The “it is a layer on top” reading is carried by the scrim over a still-visible host page and by the open animation — both drawn above — not by a 24px margin, and the run modal already made this call in this same primitive for this same reason (“at full size the dialog IS the surface”).

The four ways out — all four do the same thing
✕ Close the control top-LEFT of the workspace. A plain Close — never “Back to …”, because an overlay has no destination to name
Esc the DIALOG's handler (Radix), not the host's. The host's own keydown listener is deleted
scrim a click on the dimmed page outside the dialog
Back the address was a shallowPush, so it left a history entry; a popstate that no longer carries the overlay parameters closes it with no second history write
all four one path: requestClose() → withoutPlanningOverlay(here) → shallowPush. The host page underneath is never unmounted, so its filter, its scroll and its client islands survive
Two Esc handlers, arbitrated

The canvas's opt-in fullScreenable control is OFF inside the overlay. Escalating to the Fullscreen API from inside a dialog that already fills the screen is two overlays and two Esc handlers — the run modal's decision, verbatim, for the same reason. The host's own Esc listener (which yielded to a focused field, to document.fullscreenElement and to a defaultPrevented event) is removed: Radix owns the key, and a text field inside a dialog still keeps it, because Radix's own handler is the one that yields.

The ADDRESS — a namespaced query, settled here because three files read it

The workspace opens on ANY authed route, so its query rides beside the host page's own. Measured collisions at origin/main: ?item= is the roadmap's drilled LEVEL (MOTIR-3836), ?peek= is the quick view, and ?mode= / ?from= are generic enough to collide with anything. So the overlay's parameters are NAMESPACED and named here once — the way design/runs/ settled ?run= for its three readers.

/backlog?filter=type%3Acode&plan=project&planFrom=project

Three files agree on these four names, and none of them should be the one that picks them — the launcher module WRITES and PARSES them, the overlay READS them off useSearchParams, and the retiring /planning forward REWRITES the old mode/from/item/repo onto them. Renaming one is a change to this section first. Which vectors raise it, and what each can do
Close ✕ INTERCEPTED — nothing closes until an action is chosen
Esc INTERCEPTED. The guard's OWN Esc then dismisses the guard, never the workspace
scrimINTERCEPTED, same as Close
Back ALREADY HAPPENED. A history pop cannot be prevented — by the time the overlay notices, the address no longer carries the query. So the guard opens over a workspace whose address has already changed, and Keep planning RE-PUSHES the overlay address with one shallowPush; Discard and Confirm let the pop stand
streaming NOT guarded. A turn still streaming has produced no proposal to lose — the predicate is state.review && !state.decided && !index.isEmpty, and a stream has no review yet. Closing calls the conversation's stop and the turn is abandoned, which is the same thing navigating away did
reload NOT guarded — no beforeunload. A browser's own “leave site?” dialog cannot carry these three actions, so it would be a worse version of this one, and it fires on every reload whether or not there is anything to lose
The pending predicate is the HOST's, not a second one

state.review && !state.decided && !index.isEmpty — the exact expression PlanningWorkspaceHost already uses to decide whether PlanChangeConfirmBar is showing. If the bar is up, the guard fires; if it is not, closing is instant. The reader can see the rule, which is what makes it feel like a rule rather than a surprise.

Why an overlay, not a route — and why THIS overlay. The summoned planner is a session on top of your work, not a place you navigate to; so it mounts as the shipped Modal size="full" above the current route, and closing restores that route instantly because the route never left. The parts are all already in the product — the dialog primitive, its scrim, shallowPush, the run modal that answered the two-Esc question, the quick view that is itself a URL-driven dialog — so this amendment is a COMPOSITION, not an invention. What it decides that no implementation could decide for itself is three things: the overlay's four namespaced parameter names, the Close control's copy now that there is no destination to name, and what happens when somebody dismisses it with a proposal they have not confirmed. Onboarding stays a genuine full-page route (a dedicated first-run journey), and the plan detail stays a page inside the shell.
