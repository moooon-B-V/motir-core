Files on a guide turn — attach, paste, drop, and what Motir AI read

MOTIR-7482 · story MOTIR-7471 · decision docs/decisions/guide-turn-files.md. In the guide conversation a person can show Motir AI what they see: a screenshot, a config, a log. The file is attached to the guided card when the turn is sent, and Motir AI says in its reply what it read and what it could not.

Composed from shipped parts: the guide overlay (MOTIR-7462), the composer’s inset slot, the Attachments panel’s upload track, refusal row, dropzone, glyph and preview, the copyable code block. NEW is marked in each panel’s notes: the attach control, the tray, the file chips, the turn’s chip row, the read statement — and, from A3.9, the local-agent prompt, a ticked step corrected, and the re-plan reply.

NEW — the attach control is the ACCESS PATH. A paperclip icon button sits in the composer field’s bottom-left inset, immediately RIGHT of the shipped target-search trigger. The guide is the universal Motir AI surface, so its composer keeps the search control exactly as every other mode has it (PlanChangeComposer’s slot: absolute bottom-1.5 left-1.5); the attach control takes the next 28px (left: 34px), and the field’s left padding grows from pl-8 to 60px so text clears both. Nothing about the field’s height, Send or the running bar changes. This reverses the MOTIR-7462 guide design’s “no search in guide mode” (its § item 3), so GuideRail passes mentions again.

Its shape and colour are the search trigger’s: --radius-control, --spacing-icon-btn, a 16px glyph in --el-text-secondary; hover --el-card fill and --el-text; focus ring --focus-ring-color. It opens the OS file picker, multiple, filtered to the shipped allow-list (ALLOWED_UPLOAD_TYPES), so a refused type is greyed in the picker before it is ever chosen.

The tooltip (--el-tooltip-bg / --el-tooltip-text, --spacing-tooltip-x/y) names both other ways in: paste (⌘V / Ctrl V by platform) and drop (panel 3).

Everything else in the panel is the shipped guide overlay exactly as § Guide me through panel 2 draws it: the to-do card on the canvas, step 3 current, the step card in the rail.

The rail is the drop target, not the canvas. Each file is its own chip in the order it was added: an image as a thumbnail chip, every other type as a named chip with the shipped MIME-family glyph (AttachmentGlyph: text, PDF, archive, sheet…), name, type and size.

The cap is A3.3’s four files a turn. The composer does NOT judge what will be read. A PDF queues like any allowed file (it lands on the card); whether Motir AI reads it is said in the REPLY (panel 10), because A3.3 makes motir-core’s resolution the check that holds, not the composer.
