Changing a plan is a CONVERSATION — the plan-change mode on an established project

MOTIR-1727 · Story MOTIR-1726 — a change to the plan is always a conversation; one prompt is not enough to reshape a plan. So the one-shot “Augment from prompt” button retires and the capability moves onto the universal planning workspace. This board draws the re-plan / plan-change MODE — the entrance on a project that already HAS a plan, the multi-turn conversation, the proposed changes as a diff on the canvas (not a corner dock), the locked treatment for done work — and the two toolbars the retired button leaves behind.

This is a STATE of the one surface, not a new one. Every structural element is composed verbatim from design/ai-chat/planning-workspace.mock.html (MOTIR-1193) — the two-pane PlanningWorkspace frame, the canvas node + edge language of design/roadmap/ (MOTIR-1009), the DiscoveryChatRail language, and the confirm-to-persist bar. Its sheet 3 already names this mode; this asset draws it. Rendered against shipped reality first — the app strips below reproduce the running app’s real control order and labels (prod build, PayFlow project, AI configured).

Turn 2 REFINES turn 1 — it does not re-run it. Each turn appends to a persisted, project-scoped session and the ACCUMULATED intent is what is submitted (MOTIR-1728), so “split it” and “drop the SMS reminder” land on the proposal already on the canvas instead of starting a fresh, unrelated one. This is precisely what the retired one-shot modal could not do: there, a wrong result left you re-typing a different prompt from scratch. The session is persisted, so re-opening the workspace resumes the same thread rather than a blank rail.
Streaming. The reply streams into the rail (an aria-live="polite" region) as partial text with a caret, followed by the Spinner row while the delta is still being computed — the shipped DiscoveryChatRail drafting language, unchanged. The canvas updates incrementally as each proposed item arrives, exactly as in MOTIR-1193 sheet 2.

The corner dock is replaced for this flow. Today PlanEditsReviewDock renders the delta as a fixed bottom-right list of rows — a text list of ops, detached from the plan they change, with no way to see WHERE a proposed item lands or what it depends on. In the workspace the same delta becomes the canvas itself: each op is drawn on the node it affects, in place, with its edges. The dock stays in the codebase for the item-scoped expand / replan row actions on /items (out of scope for this story, MOTIR-1731) — it is retired from this flow, not deleted.
Done work is LOCKED, and the lock is visible — not colour-alone. A done item renders with a hatched surface + a 🔒 lock glyph + a can’t change pill + a locked corner tag, and the AI says so in the rail. This is the completion-aware guarantee made legible: the engine may propose around finished work, never over it, and an attempted immutable edit is rejected server-side.
Confirm-to-persist, and the conversation survives it. Nothing reaches the database until Approve changes; Discard drops the whole proposal and writes nothing. After either, the rail stays open — that is what makes this a conversation instead of a transaction, and it is why the flow does not close a modal on you. Closing the overlay with a proposal still pending raises the shipped close-with-pending guard (Discard N proposed · Keep planning · Approve, MOTIR-1193 sheet 6). Approving changes the work-item tree, so the canvas — a client island that owns its own state — refetches on an explicit trigger, and the server-rendered counts behind the overlay take the route refresh.

What is lost, exactly. One control on two surfaces, plus the small modal it opened (a single Input + Submit) and its three planEdits.augmentPrompt* strings in both locales. Nothing else shifts — the toolbars are a plain flex row, so the neighbour simply becomes the last control and everything keeps its order; there is no placeholder, no empty slot, no re-layout. The after strips above are the real post-removal toolbars, drawn to scale directly under their today counterparts.
What deliberately STAYS. The item-scoped expand / replan row actions on /items (PlanEditsTrigger) and their review dock, the /ready expansion nudge, and POST /api/ai/augment with its whole job path — the conversation drives that same endpoint. Only the prompt-driven one-shot entry retires. Converging the row actions onto this workspace belongs to the per-item entrance (MOTIR-812), not here.
Why this panel exists at all. Per the REMOVAL corollary of the decision-amendment rule (notes.html #154), a decision that removes an affordance must spawn its matching design amendment in the same pass — otherwise the design of record keeps depicting a control the product no longer has. This is that amendment: the post-removal toolbars are now the drawn state of record.

Not colour alone, anywhere. Each diff state pairs a border treatment (dashed accent / solid info / dashed danger / hatched) with a glyph (＋ ✎ − 🔒) and a word (added / changed / removed / can’t change), and every tinted chip puts the hue in the background with --el-text-strong ink — so the board reads for a colour-blind reviewer and holds AA. Each rail state pairs its icon with a sentence, never a bare tint.

Token discipline. Colour is the real --el-* light palette inlined at the top of this file (the sibling design/ai-chat/ convention); every non-token fill is a color-mix() of two tokens — no invented hue. Tinted chips put the hue in the background with --el-text-strong (AA). Shape maps to the element-semantic tokens: node = --radius-card, pills = --radius-badge, buttons = --radius-btn, the composer input = --radius-input, toolbar controls + rail rows = --radius-control, elevation = --shadow-{subtle,card,elevated} — so a data-style swap reshapes the surface and a data-palette swap re-skins it. rounded-full only on the status dot, avatars and the orb.
A11y. The canvas and the rail are labelled regions; the streaming reply is an aria-live="polite" region and the error is role="alert"; the diff state of a node is in its accessible name (“Recurring invoices, proposed addition”), not in its border alone; a locked node is aria-disabled and says why; Approve / Discard are real buttons in the tab order, and Esc closes the overlay through the pending guard.
