GET /api/v1/work-items/{key} read

The full work item: its own fields, its parent and children, its five link groups, its readiness verdict and its comment count. The response carries an ETag for use as an If-Match on a later update.

Request

Parameter In Description
key
string · required 		path The work item’s MOTIR-<n> key. Never its internal id.

Example

curl
curl https://app.motir.co/api/v1/work-items/MOTIR-1854 \
  -H "Authorization: Bearer motir_pat_<your-token>"

Responses

Status Body Condition
200 WorkItemDetail The work item.
401 ErrorBody Authentication required — the five token failures are deliberately undifferentiated.
403 ErrorBody The token is valid but lacks the read scope.
404 ErrorBody No such item, or it is outside this token’s workspace — the same answer, on purpose.
429 ErrorBody Budget spent. Read X-RateLimit-Reset.
500 InternalErrorBody An unexpected fault — no code, by design.

PATCH /api/v1/work-items/{key} work_items:write If-Match supported

Patch any subset of a work item’s fields. A field that is ABSENT is untouched; a field explicitly set to null CLEARS it.

Request

Parameter In Description
key
string · required		 path The work item’s MOTIR-<n> key.
If-Match
string · optional 		header An ETag from a previous read. When present, the update is refused with 412 if the item moved since that read. Omitting it means last-write-wins.

Body

application/json
{
  "title":          string?,
  "descriptionMd":  string | null?,
  "priority":       "lowest" | "low" | "medium" | "high" | "highest"?,
  "storyPoints":    number | null?,
  "parentKey":      string | null?
}

Example

curl · conditional update
curl -X PATCH https://app.motir.co/api/v1/work-items/MOTIR-1854 \
  -H "Authorization: Bearer motir_pat_<your-token>" \
  -H "Content-Type: application/json" \
  -H 'If-Match: "2026-08-05T09:51:35.667Z"' \
  -d '{"priority":"high","storyPoints":5}'

Responses

Status Code Condition
200 — The updated work item.
412 STALE_WORK_ITEM The If-Match validator no longer matches — re-read and retry.
422 ILLEGAL_PARENT_TYPE
CROSS_PROJECT_PARENT
PARENT_CYCLE 		A malformed request the caller can fix, named precisely enough to act on.
404 WORK_ITEM_NOT_FOUND No such item, or outside this token’s workspace.
◆ Every response — success and failure alike — carries X-Request-Id and the three X-RateLimit-* headers. Quote the request id in a support conversation.

Getting started

From an account to a working call, in five steps. Everything below uses the same token you mint in step 1.

1 · Mint a token

Settings → API tokens → New token. Choose the workspace it is bound to and the scopes it carries. The secret is shown once.

◆ A token is bound to ONE workspace and its scopes NARROW your role — they never widen it.

2 · Your first call

GET /api/v1/me answers who the token is and what it may do, so it is the call to make before any other.

curl
curl https://app.motir.co/api/v1/me \
  -H "Authorization: Bearer motir_pat_<your-token>"

3 · Paginate

Collections are cursor-paged. Pass the previous response’s nextCursor back as ?cursor=; a null cursor is the last page.

curl · the second page
curl "https://app.motir.co/api/v1/projects/MOTIR/work-items?limit=50&cursor=$CURSOR" \
  -H "Authorization: Bearer motir_pat_<your-token>"

4 · Read an error

Branch on code, never on error — the sentence is for a human reading a terminal and is reworded freely.

404 · application/json
{ "code": "WORK_ITEM_NOT_FOUND", "error": "Work item not found." }

5 · Read the rate-limit headers

They ride EVERY response, including the ones that failed.

response headers
X-RateLimit-Limit:     600
X-RateLimit-Remaining: 594
X-RateLimit-Reset:     1785312000
X-Request-Id:          c7771231-e18c-48bc-90c9-c1a9720436a4
▲ On a 429, back off until X-RateLimit-Reset. There is no Retry-After — an absolute instant cannot go stale in transit.

Stability & deprecation

What v1 promises, what may change without notice, and how anything is ever taken away.

Additive, without notice

  • A new endpoint.
  • A new optional query parameter.
  • A new field on a response object.
  • A new value on a field documented as open-ended.
  • A new error code for a NEW condition.
  • A raised rate-limit budget.

Never, without a new major

  • Removing or renaming a field.
  • Changing a field’s type or nullability.
  • Removing or re-purposing an error code.
  • Changing an existing status for an existing condition.
  • Tightening a limit, or making an optional parameter required.
▲ Your side of the promise. A client MUST tolerate unknown fields and unknown enum values, and MUST NOT parse the human error sentence. A client that rejects unknown fields will break on a change this page calls safe.

Deprecation

A deprecated operation or field is marked deprecated: true in the spec, carries its reason and its replacement in the description, and keeps working for the announced window. The spec is the announcement channel because it is the one artifact every client already reads.

How v2 arrives

As a second document at a second path, served alongside v1. v1 is not rewritten and does not stop working the day v2 ships; deprecating it is itself an announcement under the same window.

Run your agent in the sandbox

Motir asks you to hand work to a coding agent that runs unattended, with approvals off. This is where it runs: a published container that can reach your workspace tree and nothing else on your machine. Adopting it is a docker run, not a git clone.

Before you start

Four things, none of which involves cloning this repository. The container consumes credentials you already have — it never mints one for you.

What you need How to get it
Docker
running		 Docker Desktop or any engine. The images are built for linux/amd64 and linux/arm64, so Apple Silicon is a first-class machine and nothing is emulated. There is no build step — you pull.
A Motir token
+ server URL 		Mint one under Settings → Account → API tokens and export it as MOTIR_TOKEN (with MOTIR_SERVER). Or skip it and run motir login inside the container — see the three tiers below.
Your agent's own sign-in
on the host 		Sign in to your coding agent once, on this machine, before you start — or pass its API key through the environment. The credential mount is read-only, so the container can use a sign-in but can never perform one.
A linked workspace
.motir.json 		Run motir link in the folder that HOLDS your checkouts — not inside one of them. See below.

Your workspace root, and .motir.json

A Motir project usually spans several repositories, and motir auto dispatches across all of them — so the thing the container mounts is the folder that contains your checkouts, not any one checkout. That folder is your workspace root, and motir link marks it by writing .motir.json there:

your machine
~/work/                 ← the workspace root. Run docker from HERE.
├── .motir.json         ← motir link writes this
├── motir-core/         ← a checkout
└── motir-ai/           ← another

.motir.json is just the link — serverUrl, workspace, project, and an optional repos map for a checkout that is not named after its repo. It holds no secret and is safe to commit. Commands resolve it by walking upward from wherever you are, so they work from inside any checkout — but the docker run is the one thing that must start at the root, because that is what gets mounted.

◆ motir doctor checks all four and names what is missing. Run it on the host before you start, and again inside the container if a run stops early — it is the same command in both places.

What it confines — and what it does not

Surface
Filesystem Confined. The only host surfaces inside the container are a writable /workspace and, if you mount them, a read-only Motir credential and your agent's own. No docker socket, no other host bind.
Network Open, by design. Every agent needs its provider API, and every dispatched item needs git remotes. This image confines the filesystem blast radius, not egress — reach for docker's own --network controls if your threat model needs more.
Privileges Runs as the unprivileged node user (uid 1000), so files written into the mount stay owned by you rather than by root.

Choosing a profile

One image per agent, each layer fetching that CLI from its own official source at build time. Pick the tag that matches the agent you already use; the credential column is the directory that agent keeps its own sign-in in, mounted read-only.

Run it

One command, shaped by the row you just picked. Three of its parts come from that row — everything else is the same for every profile:

sh · the shape
docker run --rm -it \
  -v "$PWD:/workspace" \
  -e MOTIR_TOKEN -e MOTIR_SERVER \
  -v "$HOME/<credential mount>:/home/node/<credential mount>:ro" \
  ghcr.io/moooon-b-v/motir-sandbox:<profile> \
  motir auto --agent "<your agent's command>"
The part Comes from For claude
<profile> the Profile column above claude
<credential mount> the Credential mount column above, with its ~/ written as $HOME/ .claude
<your agent's command> your agent's own non-interactive + auto-approve flags. They drift between vendor releases, so the current set lives beside the image in packages/cli/sandbox/README.md § Auto-approve flags — check yours there rather than here. claude --dangerously-skip-permissions

A profile with two credential mounts (opencode) takes two -v lines; one with none (antigravity) takes none at all, and signs in through its own keyring on the host. Filled in for claude, that is:

sh · copy, then swap the three parts for your row
docker run --rm -it \
  -v "$PWD:/workspace" \
  -e MOTIR_TOKEN -e MOTIR_SERVER \
  -v "$HOME/.claude:/home/node/.claude:ro" \
  ghcr.io/moooon-b-v/motir-sandbox:claude \
  motir auto --agent "claude --dangerously-skip-permissions"

Run it from your workspace root — the folder holding .motir.json, not a checkout inside it. With no command after the image name you get an interactive shell in /workspace instead.

What each part is for

Mount / variable Why
$PWD:/workspace Required, writable. Your .motir.json tree — the only host path the agent can change.
MOTIR_TOKEN · MOTIR_SERVER The Motir credential, from the environment. Needs no host state at all, so it is the CI and fresh-machine path.
~/.config/motir:…:ro Optional, read-only. A credential you already have on this host — an alternative to the two variables above, not a requirement.
~/.claude:…:ro Read-only. The agent's own credential — the row you picked above.

Three ways to give it a Motir credential

The container needs a token for your Motir server, and has the same three tiers the CLI has anywhere else. 1 · Pass them through with -e MOTIR_TOKEN -e MOTIR_SERVER — nothing mounted, nothing written to disk. 2 · Run motir login inside the container — a device grant you approve in a browser on any device. 3 · Mount a credential you already have, read-only.

◆ motir login needs the credential mount to be absent — with a read-only bind over it, ~/.config/motir is not writable and the login has nowhere to land.

Or set it up in VS Code

The same confined image, as a dev container: VS Code opens /workspace inside it with the same mounts, so your editor, terminal and agent all run behind the same boundary. Three steps.

◆ It is the SAME image, so everything in Before you start still applies — Docker running, a Motir credential, your agent's sign-in already on the host, and a linked workspace root. The dev container adds exactly one thing to that list: the extension in step 1.

1 · Install the Dev Containers extension

From the Extensions view, or the command palette's Extensions: Install Extensions. It is what starts the container on your behalf — VS Code does not ship it, and it drives the same Docker engine the command above uses.

2 · Add .devcontainer/devcontainer.json to your workspace root

Beside your .motir.json. Pin the published image and the mounts your profile needs — this is the same set the docker run above passes:

.devcontainer/devcontainer.json
{
  "name": "Motir sandbox (Claude Code)",
  "image": "ghcr.io/moooon-b-v/motir-sandbox:claude",
  "workspaceFolder": "/workspace",
  "workspaceMount": "source=${localWorkspaceFolder},target=/workspace,type=bind",
  "mounts": [
    "source=${localEnv:HOME}/.claude,target=/home/node/.claude,type=bind,readonly"
  ],
  "remoteUser": "node",
  "overrideCommand": true,
  "postAttachCommand": "motir doctor",
  "remoteEnv": {
    "MOTIR_TOKEN": "${localEnv:MOTIR_TOKEN}",
    "MOTIR_SERVER": "${localEnv:MOTIR_SERVER}"
  }
}

Swap :claude and the mounts entry for your profile's row in the matrix above. remoteEnv forwards your Motir credential from the local environment, so a machine that never ran a host login still resolves one.

3 · Reopen in Container

Command palette → Dev Containers: Reopen in Container. VS Code pulls the image, attaches, and postAttachCommand runs motir doctor so a missing credential shows up in the terminal on the way in, rather than mid-run.

▲ The devcontainer.json files committed under packages/cli/sandbox/devcontainer/ are not this file. They carry a build block pointing at the repository's own Dockerfile, because they are motir-core's dev containers and a checkout is what those are for. For your own workspace, pin the image as above.
◆ This page is the first ten minutes. Digests to pin, the confinement proof, the validation harness and the escape hatch for an unlisted agent live in packages/cli/sandbox/README.md.
