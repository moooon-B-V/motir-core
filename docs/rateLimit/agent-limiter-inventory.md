# Agent rate-limit inventory (MOTIR-8598)

The inventory every re-key card in Story [MOTIR-8548](motir:cmv7wttiz00bshvshh28djc16) builds from.
It records each rate-limit call in motir-core: who reaches it, how it is keyed and sized today,
how it is keyed and sized under the story's model (volume per agent plus a per-workspace ceiling,
money per `(workspace, user)`), and whether its counter write can run inside a request
transaction. It changes no limiter.

## Headline findings

1. **The job read-backs no longer draw the 30/min money budget.** On the measured SHA, `ai:internal`
   draws `aiInternalBudget()` (600 / 60 s, `MOTIR_AI_INTERNAL_RATE_LIMIT`), still keyed per
   `(workspace, user)`. [MOTIR-8423](motir:cmv7163ni0061hvoi0q51x1f8) shipped that in motir-core
   #3573. What is still wrong is the KEY: every job one person runs shares one 600/min bucket.
   [MOTIR-8604](motir:cmv8bffsn0148hvoir5jpz8so) moves it per job.
2. **Four agent-reachable surfaces, three refusal shapes, one machine-readable seconds field.** Only
   the MCP transport puts `retryAfterSeconds` in its body. The job-token 429 and the v1 429 carry
   the seconds only in prose (v1 also lacks `Retry-After`). A billable tool carries them only in
   prose. [MOTIR-8600](motir:cmv8bffkm0140hvoimc6odzjg) fixes all four. Two more agent-reachable
   refusals sit outside that card (see _Findings not owned_).
3. **No counter write runs inside a request's interactive transaction.** Every limiter writes
   through `rateLimitService.increment`, which opens its own one-statement `db.$transaction` on the
   pooled `db` singleton. Every call site runs at a route edge or a service method's top level,
   before the caller opens a transaction. The open cost is that each limited request holds a second
   pool connection for one statement; that cost is the load-test's to measure
   ([MOTIR-8609](motir:cmv8bfg7b014ihvoiv9gbew6k)).

## Corrections to the story's premise

The story's _Where this starts_ was read before [MOTIR-8423](motir:cmv7163ni0061hvoi0q51x1f8)
merged. On the measured SHA:

- **`ai:internal` draws `aiInternalBudget()`, not `aiBudget()`.** `enforceAiRateLimit`
  (`lib/rateLimit/aiGuard.ts:37`) picks `aiInternalBudget()` for `ai:internal`:
  `DEFAULT_AI_INTERNAL_RATE_LIMIT = 600` per `60_000` ms (`lib/rateLimit/budgets.ts:95`), env
  `MOTIR_AI_INTERNAL_RATE_LIMIT`. Key unchanged: `rateLimitKey('ai:internal', workspaceId, sub)`.
  So the story's _"`ai:internal` … drawing `aiBudget()` = 30/min"_ and criterion 6's _"no longer
  spend `aiBudget()`"_ are already true. What remains for criterion 6 is the per-JOB key, so that
  two jobs of one person do not share 600/min.
- **`enforceInternalServiceRateLimit` still draws `aiBudget()` (30 / 60 s)**, under scope
  `ai:internal`, keyed `rateLimitKey('ai:internal', 'service', <presented service bearer>)`. That
  is ONE bucket for every service-bearer call motir-ai makes as the system principal, across every
  tenant: `live-organizations`, `live-projects`, and the four `work-items*` routes motir-ai's bug
  filing uses (`createBug`, `commentOnFiledBug`, `attachFileToWorkItem`, `updateFiledBugDescription`).
  The story does not name it. See _Findings not owned_.
- **Job-token routes: 28, not "~15".** `lib/ai/jobAuth.ts`'s comment on `JobRateLimitedError`
  says "the ~15 `/api/internal/ai/*` routes". Pattern 1 finds 28 call sites in 26 route files
  (`plan-proposals/[itemId]` and `plan-proposals` each call it twice, once per verb), including
  `job-token/refresh`. The refresh route draws the same per-user bucket as the reads it keeps
  alive, so a busy user could see a REFRESH refused for rate, which would end a long job at
  `token_invalid` once the old token expires. The per-job key in
  [MOTIR-8604](motir:cmv8bffsn0148hvoir5jpz8so) covers it, because it re-keys the shared function.
- **The MCP billable-tool money surface has a sibling the story does not list.**
  `search_lessons` and `search_work_items_semantic` each spend `ai:chat` (30 / 60 s, per user,
  shared with the browser chat) because each embeds the query. They are money, so their key and
  budget stay. Their refusal shape is the gap (below).
- **The MCP transport refusal is already compliant.** `mcpRateLimitedResponse` carries
  `error.data.code = 'RATE_LIMITED'`, a numeric `error.data.retryAfterSeconds` and `Retry-After`.
  [MOTIR-8600](motir:cmv8bffkm0140hvoimc6odzjg) only pins it.

## MOTIR-8423

**(a) Did a 429 from `ai:internal` produce "could not be read for this user"?** Yes, by the
evidence recorded on [MOTIR-8423](motir:cmv7163ni0061hvoi0q51x1f8) (diagnosis comment,
2026-10-13 19:15Z). It quotes the failing read at the time,
`const targetView = await getItem(jobToken, targetKey).catch(() => null)` followed by
`throw new ApiError('validation_error', 'planning: the target … could not be read for this user')`,
and the production counter for that user's `ai:internal` key: _"59 in the 18:44 window, then 132
at 18:45 and 86 at 18:46"_ against a 30/min budget, at the minute the target read happened. The
comment notes the 429 itself was not visible in core's logs: _"The counter, the timing and the
code path are the evidence."_ So the cause is settled by inference from the counter, not by a
captured 429. Both halves of the fix shipped (motir-core #3573 raised the budget to 600/min;
motir-ai #744 retries the target read).
